**Working principles** *(standing methodology, not a one-time note)*
- **Scope by root cause, not by component.** When a finding recurs across multiple independent files/screens — the same underlying symptom or defect shape, not just superficially similar bugs — treat it as one body of work to be scoped and planned together, not fixed one instance at a time as separately-discovered bugs. This project has already demonstrated the pattern more than once before it was named: the fuzzy-matching false-positive bug (same root cause across the branded pack, JSON Import, and ReviewScreen's silent auto-merge, fixed as one investigation rather than three); the atomicity gaps (same missing-transaction shape across `mergeIngredients()`, `performReset()`, `applyReceiptSaveBatch()`, `resolveIngredientDuplicate()`/`resolveRecipeDuplicate()`, and `executeImport()`); and now the Operation Feedback & Trust work (Cloud Sync, Backup Import, JSON Import, Bulk Entry, and Starter Library loading all independently missing the same kind of long-running-operation feedback). When a new finding looks like it might be one of these, check for siblings before scoping a fix narrowly.

- [ ] **New, found during the casing-remediation review — case-insensitive `is_member_of_code()`/`is_writable_member_of_code()` (Option B) is deliberately deferred, and is unsafe to implement standalone if ever picked up.** `households.code` has a case-*sensitive* unique constraint — nothing stops a second, genuinely different household from being created with a code that's a case-fold of an existing one (e.g. `angelo-family-2026` as a distinct new household, not a typo of the real one). If the two RLS helper functions are made case-insensitive without also fixing this, an attacker could create their own household with a case-folded variant of a target's code, and `lower(h.code) = lower(p_code)` would then grant them real membership-based access to the target's exact-cased data — turning "must know the exact code" into "must know the code in roughly any casing." No current collision exists among the 7 real `households` rows (checked live), so this isn't an active problem — but if Option B is ever implemented, it must ship together with a case-insensitive uniqueness constraint on `households.code` (e.g. `create unique index on households (lower(code))`), not as a standalone 2-function change. Deferred for now: the confirmed-historical casing drift is fully fixed by the normalization above, which removes the current need for this.
- [ ] **New, found during the casing-remediation review — `fetchCloudRows()`/`upsertCloudRow()`/`deleteCloudRow()` (`db/supabase.ts:660-694`) remain case-sensitive and are a separate, unaddressed gap from Option B.** All three use a plain `.eq('household_code', code)` / literal write — independent of RLS entirely, and untouched by both the data normalization above and any future Option B fix. A future re-drift (any of the 3 free-text code-entry points — Settings' Household Sync Code field, Account's Create Household form, Account's Join Household form — none of which normalize casing today) would still cause silently-missing data client-side even with Option B in place, since these 3 functions would simply never request the mis-cased rows. Needs its own scoped fix (client-side canonicalization at the entry points, or switching these 3 functions to `.ilike()`) — explicitly not bundled into the casing remediation or into Option B.
