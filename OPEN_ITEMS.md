- [x] **Investigated and fixed: Receipt Scanner confidence-badge labeling accuracy, 2026-07-25.** Last remaining item from the Functional Risk batch's reclassified "UI Trust / Labeling" bucket. Investigated fresh against current code rather than trusting the prior audit's conclusion, per instruction — and the prior conclusion turned out to be **partially wrong**: `git blame` traced "Barcode match" vs. `TIER_LABEL['high']` ("High confidence") back to `ee0af0c`, the very first commit that added Receipt Scanner — the two badge texts were **never actually identical**, at any point, contrary to what the tracked item claimed. Match provenance (`RankedCandidate.source: 'barcode' | 'name'`) does reach the UI today and is used correctly in two places: the per-line header badge (barcode-single-match renders "Barcode match", name-single-match renders "High confidence" — different text) and the candidate-picker list (each candidate tagged "barcode" or "name match"). **The real, still-live problem was one level deeper and more serious than a wording nitpick**: `findSmartMatches()` (`smartDuplicate.ts`) is a flat pass/fail with no internal reason code — exact string equality, close edit-distance (≤2), and one-directional keyword-subset matches (e.g. "Lime" matching "Key Lime Pie Filling" purely because both contain "lime") all collapse into the same boolean result, so a *lone* match from any of those three signals got `tier: 'high'` identically. Classification: **misleading**, and a real functional risk, not merely cosmetic. **Fix chosen — confidence-tier change, not badge/text/compare-card changes**: `matchLine()` (`receiptMatching.ts`) now only assigns `tier: 'high'` to a lone name match when it's a genuine exact-name match (`candidates[0].ingredient.name` case/whitespace-insensitively equal to the parsed line name); a lone match from edit-distance or keyword-subset alone now gets `tier: 'medium'`, which routes it through the exact same "Pick a match" human-review path (forced candidate list, nothing pre-selected, `mode: 'pending'`) already used for every other ambiguous line — no new UI component was built. Considered and rejected: explanatory text alone and a new badge/visual system (neither would have closed the actual auto-select/zero-click-save gap, only re-worded or re-colored it); a second independent "data completeness" confidence dimension (no real signal exists to back one — Receipt Scanner doesn't compute a completeness score at match time, so it'd be fabricated complexity); reusing ReviewScreen's side-by-side compare card (that pattern fits ReviewScreen's single-item flow — Receipt Scanner is bulk/multi-line by design and its existing lightweight candidate-list + per-candidate source-tag pattern is the proportionate equivalent, already built, just not previously reached by the lone-fuzzy case). **Verified**: 12/12 checks in a byte-faithful port of the actual `editDistance`/`keywords`/`findSmartMatches`/`matchLine` logic (copied from the real files, not paraphrased), run against realistic catalog fixtures for all 4 required match paths — barcode single-hit, exact-name lone match ("SPANISH RICE"), fuzzy-name lone match ("Lime" → "Key Lime Pie Filling," the real risk case), and multi-candidate ("Rice" → 3 candidates) — including a downstream check proving the old code's `mode: 'match'` (auto-selected) becomes the new code's `mode: 'pending'` (blocked until explicit pick) for the fuzzy-lone case, with the exact-name and multi-candidate paths unchanged (no regression). A direct import of the real TS module (rather than a port) was attempted first via Node's native TS support but blocked on extensionless relative imports Node's ESM resolver can't follow without Vite's bundler; the port is copied verbatim from the current file content, not reconstructed from memory. Build-verified. **Not click-verified live**: reaching this exact scenario through the real workflow requires a photographed receipt whose Gemini OCR output happens to fuzzy-match exactly one real household ingredient by keyword-subset rather than exact name — not reliably constructible without either fabricating a receipt image or depending on unpredictable OCR output, and risking a wrong price/variant write against real production data if the scenario didn't land as intended; deliberately not attempted, same judgment call as StarterLibraryPrompt's skipped live test above.
