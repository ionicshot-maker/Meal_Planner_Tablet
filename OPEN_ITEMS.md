**Active bugs, ranked by severity** *(full risk analysis — call chains, concrete triggers, verified examples against real data — lives in the 2026-07-24 audit conversation, not repeated here)*

*Silent Data Corruption Risk:*
- [ ] `ReviewScreen.tsx handleSave()` (shared by Barcode/USDA/Gemini/Scan Label imports) silently auto-merges a new item as a variant of an existing ingredient with **zero confirmation** whenever `findSmartMatches()` returns exactly one match and there's no brand conflict — only ≥2 matches, or a brand conflict, shows the "Similar Ingredient Found" review modal. Same loose fuzzy-matching logic already confirmed to false-positive for JSON Import (fixed 2026-07-24). Verified against the real, currently-shipped 440-item starter library — confirmed single-match false positives exist right now, e.g. "Turkey Bacon" → silently merges into "Bacon". Also has a bare `catch { setSaving(false) }` with no error message shown on any failure. Affects the 4 most commonly used single-item import paths during normal, everyday ingredient additions.
- [ ] Barcode comparison divergence: `findBarcodeMatch()` (`smartDuplicate.ts`), `findIngredientByBarcode()` (`db/ingredients.ts`), and `ReviewScreen.tsx`'s inline barcode check (line ~189) all do plain `===` string comparison with **no checksum validation and no leading-zero normalization** — only Receipt Scanner's `matchLine()`/`barcodeValidation.ts` has that. Can reproduce the already-fixed leading-zero duplicate bug via barcode scanning or manual entry (not just CSV import): a barcode stored pre-v5-fix without its leading zero won't match a fresh camera scan of the same product, falls through to fuzzy name matching, and can trigger the ReviewScreen silent-merge bug above or create a genuine duplicate ingredient.

*Data Integrity/Consistency Risk:*
- [ ] `mergeIngredients()` (`db/mergeIngredients.ts`) is not atomic — recipes/grocery-lists/macro-logs repointing, ingredient deletion, and category reconciliation are 5 separate sequential writes, no shared transaction. Interruption after repointing but before deletion leaves a harmless-but-orphaned duplicate ingredient; interruption after deletion but before category reconciliation is **not recoverable by retry** (retrying throws immediately since the merge-away ingredient no longer exists) — category must be fixed by hand. Distinct from the already-shipped category-picker UI feature (2026-07-24, see Recently Completed) — this is about write atomicity, not the picker itself.
- [ ] `resolveIngredientDuplicate()`/`resolveRecipeDuplicate()` (`db/supabase.ts`, Cloud Sync's duplicate-resolution path) never repoints `variantId`, grocery lists, or macro logs — only `Recipe.ingredients[].ingredientId`. Same incompleteness class `mergeIngredients()` was built to fix, never backported here (previously noted in `MealPlannerApp_Reference.md`'s 2.9 changelog entry, tracked here now too).
- [ ] `DataSection.tsx performReset()` (Settings → Data → Reset) clears multiple IndexedDB stores in a sequential loop with **zero try/catch of any kind** — no shared transaction and no error shown to the user if it fails partway through, despite "reset X" being an all-or-nothing user intent.

*Functional Risk (batched — common root cause: missing error handling around sequential per-item write loops, meaning a mid-loop failure can hang the UI in a stuck "saving/importing" state with no visible error, though already-saved items remain individually valid and safe to retry):*
- [ ] No try/catch around the save loop in: `JsonImportTab.tsx handleImport()`, `BulkEntryTab.tsx handleSaveAll()`, `StarterLibraryPrompt.tsx`'s silent auto-seed effect (empty-install/legacy-migration paths — can strand the "Updating ingredient library…" toast), `DataSection.tsx executeImport()` (has an outer catch, but the generic "Import failed" message can understate partial success since some of its 7 sequential per-store transactions may have already committed). Also in this bucket: Receipt Scanner's "High confidence" badge doesn't distinguish an exact name match from a lone fuzzy match, which can overstate certainty even though a human review step exists before commit.

**New ideas, not yet scoped**
- [ ] Bill due-date awareness relative to payday (explicitly NOT a budget/amount tracker — just "here's what's due before your next payday," reusing existing payday-schedule infrastructure)
- [ ] Standalone PLU lookup capability for Receipt Scanner produce items — a static IFPS PLU→generic-produce-name table (e.g. `4038` → Raspberries, `4048` → Bananas), no API/network call/schema change needed (resolves to a name/category hint, not a `variant.barcode` match). Found while verifying why Blueberries/Raspberries on a real receipt only got NAME MATCH suggestions despite numeric codes being present: confirmed **by design, but not for this reason** — `isValidBarcodeChecksum()` (`src/utils/barcodeValidation.ts`) hard-rejects anything that isn't exactly 12/13 digits, so a real 4-5 digit PLU code is rejected before ever reaching ingredient lookup; separately, the Gemini extraction prompt (`netlify/functions/gemini-receipt-scan.ts`) describes the `barcodeText` field as "UPC/PLU, typically 11-13 digits" — internally inconsistent, since real PLU codes are 4-5 digits, not 11-13. No PLU-handling logic exists anywhere in the codebase today (confirmed via full-repo search). Not a bug — current behavior is consistent with the existing UPC/EAN-only design — but a real, unbuilt capability gap for a receipt category (produce) that's extremely common.
