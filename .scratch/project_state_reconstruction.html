Executive Summary

EvidencePer README.md: "A personal meal planning PWA for tablet and phone. Plan your week, track nutrition, and generate grocery lists automatically — all in one place, offline-capable, with no subscription required." Built for a single family ("Angelo Family Meal Planner"), React 18 + TypeScript + Vite, local-first on IndexedDB, with optional Supabase cloud sync and pluggable AI (Gemini/Anthropic/OpenAI/Ollama) proxied through Netlify Functions. Deployed via direct netlify deploy --prod, not git-triggered CI.

EvidenceMajor systems, per README.md and MealPlannerApp_Reference.md: Ingredient Database (barcode/USDA/Gemini lookup), Cookbook (AI recipe import, now multi-recipe photo cropping), Meal Planner, Grocery List, Macro Tracker (with a TDEE/BMR calculator shipped across 4 phases), Cloud Sync (Household Sync + Family Share), Settings, and a built-in Help system. Current documented version: MealPlannerApp_Reference.md's header reads v2.37, dated 2026-08-02.

InferenceThe evidence points to a project in a stabilization / audit-remediation phase, not active feature expansion. A full 8-phase application audit (AUDIT_PHASE0–7, dated 2026-08-01) was followed by roughly ten days of systematic fixes closing nearly every finding it raised, then a separate "Documentation & User Guidance Audit" effort running through 2026-08-11. The one active feature thread — Recipe Import Workflow Improvements — is itself paused mid-sequence (Phases 1, 2A, 2C-1, 2C-2 shipped; Phase 2/3 not started). The most recent git commit (2026-07-27) adds a regression-test corpus rather than new functionality, consistent with a hardening posture.

EvidenceGit shows the branch is 1 commit ahead of origin/master, with 61 tracked files modified (+2,569/−488 lines) and 19 untracked files — including all nine AUDIT_*.md files and a tenth (AUDIT_TIER2_SLICE1...) — sitting uncommitted in the working tree. 04

Security & Data Integrity Status

Independently inspected directly against the current working-tree src/db/supabase.ts — not taken on the audit documents' word.

Bottom line: the pre-Phase-3 bridge/legacy-access clause is fully retired from executable SQL — confirmed by reading the actual policy bodies, not by trusting AUDIT_CANONICAL.md's claim that it was. Two cosmetic remnants (a stale comment, and policy names that still contain the word "legacy") remain, and are documentation artifacts, not functioning access paths.

The membership check, as it exists in the file today

is_member_of_code(p_code): select exists ( select 1 from households h join household_members hm on hm.household_id = h.id where h.code = p_code and hm.user_id = auth.uid() ); is_writable_member_of_code(p_code): — identical, plus "and hm.role != 'readonly'"
src/db/supabase.ts, AUTH_MIGRATION_FIX_SQL — no OR clause, no literal household code, no bridge of any kind

All 8 data-table RLS policies in the current (superseding) AUTH_MIGRATION_FIX_SQL call these two functions directly, with no additional disjunct. The original AUTH_MIGRATION_SQL script was itself edited in place to remove the same clause from its own policy bodies.

Stale comment — not a functional gapCosmetic

AUTH_MIGRATION_FIX_SQL's own header comment still reads: "this only replaces the policy logic, using the same bridge (legacy code OR real membership) as before" — but the policy bodies beneath it contain no bridge. The comment was never updated when the bridge was retired from this script's body. The SQL itself is bridge-free; only the comment describing it is wrong.

Policy naming artifact — not a functional gapCosmetic

Policy names such as "select: legacy code or member" still contain the word "legacy," carried forward from prior drop policy if exists statements for continuity. The name doesn't reflect what the policy body actually checks.

Re-confirmed fresh 2026-08-08: no safeguard exists in the RLS policy, removeMember(), or AccountSection.tsx. A household's sole owner can remove their own membership and leave the household ownerless.

join_household_by_code()'s new optional role parameter guards against privilege escalation: any value other than 'contributor'/'readonly' — including an attempt to pass 'owner' — silently falls back to 'contributor'. A re-join never overwrites an existing role. No RLS policy changes accompany this migration; it only extends the RPC function.

Recommended Next Step

InferenceTaking this over cold, two things stand out above everything else in §06: one is urgent because it's unprotected (a single confirmed, well-understood security gap), and the other is urgent because it's fragile (weeks of security-critical work sitting outside version control).

First, commit or branch the current working tree before touching anything else. It costs nothing, and it's the only step that protects the RLS rewrite, the casing fix, and the entire Family Share migration against being lost to a bad checkout or a wiped machine — none of it exists anywhere else.

Second, close the owner-self-removal gap. It's the last standing item from a genuinely thorough, adversarial eight-phase audit that resolved almost everything else it found, the fix surface is narrow and already root-caused, and — unlike the accepted-limitation items in §03 — nothing about it has been deliberately deferred. It's simply the one thing nobody has gotten to yet.

Everything else — the legacy-key deactivation, the draft-recovery gap, the remaining documentation-audit slices, the paused Recipe Import phases — is lower-urgency by the project's own prior analysis or explicitly deferred by a decision already on record. There's no evidence in this repository that any of it needs to jump the queue.
