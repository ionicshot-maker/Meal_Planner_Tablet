## 2. First-Run Experience

Three separate first-run overlays exist, gated by settings flags so they never stack on top of each other:

1. **`SetupWizard`** — first thing a brand-new install sees. Household naming + basic setup. Can be skipped and finished later in Settings (a "Skip for now" option exists at each step).
2. **`StarterLibraryPrompt`** — offers two fully independent, optional starter ingredient packs (see below). Self-migrates if the household already has legacy-named ingredients from an older single-pack version of this component. Its loading state is one of five long-running operations governed by `OPERATION_FEEDBACK_STANDARD.md` — wired to `OperationStatus` as of Phase 3 (2026-07-25, see Section 5); the roadmap is now closed.
3. **`CloudSyncPrompt`** (added 2026-07-22) — a one-time-per-session explainer shown to anyone not signed in, explaining Cloud Sync/sign-in and linking directly into Settings → Data → Cloud Sync. Checking "Don't show this again" persists the dismissal (device-local, `cloudSyncPromptDismissed`); a standalone toggle in Cloud Sync settings can turn it back on. A brand-new device always sees it once, regardless of another device's dismissal — this is deliberately never synced.

A **Setup Checklist** widget also lives at the top of the Settings page (`SetupChecklist.tsx`) — a persistent, collapsible progress card tracking 5 required steps (household name, a person profile, first ingredient, first recipe, first planned meal) and 3 optional ones (USDA key, Gemini key, Cloud Sync). Functions as an ongoing "getting started" reference independent of the one-time wizard. It does not track either starter pack's status.

### Two independent starter ingredient packs (2nd pack added 2026-07-23, USDA set expanded 2026-07-24)

`StarterLibraryPrompt.tsx` offers both, each tracked by its own settings flag so loading (or declining) one never affects the other:

| | 440-item USDA set | 867-item Great Value set |
|---|---|---|
| Data source | Hardcoded shorthand array, `src/db/starterLibrary.ts` (`DEFS`) — bundled directly into the JS build | Static JSON file, `public/data/great-value-starter.json` (~1.1MB) — fetched at runtime, never bundled into the JS build |
| Settings flag | `starterLibrarySeeded` + `starterLibraryVersion` | `brandedLibrarySeeded` |
| Auto-seeds silently? | **Yes** — a completely empty install gets these with no prompt at all | **No, never** — always requires an explicit choice, on any install state, even a brand-new empty one |
| Content | Generic raw ingredients (meats, produce, dairy, grains, seasonings) — USDA macros, no barcode/brand/price/Nutriscore/Nova/allergen fields exist in the format at all | Real branded products — barcode, Nutriscore, Nova group, allergens, store, package size, sourced from Open Food Facts |
| Dedup on load | Simple exact-name-match only (`seedStarterLibrary()`) | Barcode + exact-name match, reusing `findIngredientMatch()` from `importNormalization.ts` — the same matching JSON Import uses — but with fuzzy name matching deliberately **off** (see below) |
| Seed logic | `src/db/starterLibrary.ts`, `seedStarterLibrary()` | `src/db/brandedLibrary.ts`, `seedBrandedLibrary()` |

**Why fuzzy matching is off for the branded pack — and, since 2026-07-24, off for JSON Import too:** `findIngredientMatch()` supports an optional fuzzy-name fallback on top of barcode/exact-name, via `findSmartMatches()`'s keyword-subset and edit-distance checks. Testing the branded pack against the tiny 101-item generic set surfaced a real false-positive problem — multi-word branded names like "Whole Milk" or "Creamy Peanut Butter" fuzzy-matched against short generic names like "Milk" or "Butter" a large fraction of the time (roughly half the 867 items got wrongly skipped as "duplicates" in testing) — so the branded pack's seed call was given `{ fuzzy: false }` while `JsonImportTab.tsx`'s own call was left on its old default (fuzzy on), on the reasoning that this was "JSON Import's existing behavior, unchanged." **That reasoning turned out to be wrong — it was the same bug, just not yet triggered.** Confirmed live 2026-07-24: importing a 366-item generic USDA file via JSON Import's Add New Only mode against the real ~6,100-item household database reported 0 added, 366 skipped — but only 242 were genuine duplicates. The other 124 (e.g. "Lime", "Watermelon", "Carrot") each fired a spurious fuzzy match — "Lime" alone matched "Rice" (edit distance 2, unrelated foods) and multiple unrelated multi-word names containing "lime" as a keyword. `JsonImportTab.tsx` now also passes `{ fuzzy: false }`, matching the branded pack. `findIngredientMatch()`'s `{ fuzzy?: boolean }` option itself is unchanged — both of its two callers now opt out of fuzzy matching, leaving barcode + exact-name as the only ways either import path treats something as a duplicate.

**Related risk, fixed 2026-07-24:** `ReviewScreen.tsx` (shared by Barcode Lookup/USDA Lookup/Gemini Lookup/Scan Label — not JSON Import) used to call `findSmartMatches()` directly and, when it returned **exactly one** match with no brand conflict, silently merge the new item in as a variant of that match with **zero user confirmation** — confirmed live against the real starter library, e.g. "Turkey Bacon" silently merging into "Bacon". `handleSave()` no longer has that shortcut: any match count ≥ 1 now always shows the "Similar Ingredient Found" modal and requires an explicit click, with a new side-by-side compare card (name/brand/category/macros/barcode) for the draft and each candidate so the user has enough information to judge whether it's really the same product. **Live-verified 2026-07-24 by the user directly**: searching "Ramen Noodles" in production correctly surfaced the confirmation modal with several fuzzy candidates and their compare cards instead of silently merging; none were the same product, so the user chose Save as New. Confirms the modal/compare-card mechanism works end-to-end against real data; this specific search hit the ≥2-match branch rather than the exact single-match branch that originally triggered the bug, though both share the same underlying code guarantee. See the 2.14 changelog entry and `OPEN_ITEMS.md`.

**USDA set expansion, 101 → 440 (2026-07-24):** the same 366-item `usda_comprehensive.json` used to surface the JSON Import bug above was merged directly into `starterLibrary.ts`'s `DEFS` array, converted into the file's existing shorthand (`IDef`/`VDef`) format. Deduped by name (case-insensitive) against the **existing 101 `DEFS` entries specifically** (not the household's live database, which is a different, much larger comparison — 242 of 366 matched there, but only 27 of 366 matched the clean 101-item set) — 27 overlaps skipped, **339 genuinely new entries added**, bringing the set to 440. `usdaFdcId` was checked and confirmed **absent from every one of the 366 source items** (not "present for some, preserved" as originally assumed going in) — none of the 339 new entries carry one, unlike a meaningful fraction of the original 101.

**⚠️ Real data-quality issue found in the source file, handled by omission:** `saturatedFat` and `transFat` are literally `0` for all 366 items with zero exceptions — including foods like Ground Beef 80/20, Bacon, and Salmon that obviously have substantial saturated fat in reality. Confirmed this is a placeholder/unpopulated field, not real data (other fields — fiber, sugar, protein, carbs — vary normally across the same 366 items, so it's isolated to these two fields). Per the user's explicit decision, `sf` (saturatedFat) is **omitted entirely** from all 339 new entries rather than shipping a false "0g saturated fat" claim as default seed data — matches how the original 101 already treats `sf` as optional/sometimes-absent. `transFat` was never part of the shorthand format's `VDef` interface at all, so nothing needed to change there.

**Category chip list fix:** `StarterLibraryPrompt.tsx`'s USDA prompt shows a curated, hand-maintained category chip list that does **not** auto-derive from `DEFS` (confirmed — a known trap from an earlier audit). The 339 new entries introduced 4 categories the old 10-chip list didn't have: **Rice & Grains, Dry Beans & Legumes, Pasta & Noodles, Soups & Broths** — all 4 added to `USDA_CATEGORY_CHIPS`, a new named constant (previously an inline array) now shared by both the first-time prompt and the growth-offer prompt below. All 12 categories the new entries actually use were also confirmed already present in the app-wide default `ingredientCategories` list (`db/settings.ts`) — no changes needed there.

**Version bump and migration for existing installs:** `starterLibraryVersion` bumped from the implicit `2` to a named `CURRENT_STARTER_VERSION = 3` constant (every previously-hardcoded `2` literal in `StarterLibraryPrompt.tsx` now reads from this constant). This was a genuine design decision, not a mechanical bump — the old code's `usdaResolved = version >= 2` gate meant that once true, the branch controlling USDA prompting/seeding **never runs again**, so merely expanding `DEFS` without touching the version would have permanently hidden the new 339 items from any household that had already been through the flow. The two obvious alternatives were rejected: silently topping up every already-seeded household (would add ~339 ingredients with zero confirmation, even for someone who explicitly *declined* the original 101 — the existing `starterLibrarySeeded` flag is set to `true` on decline too, so accept vs. decline can't be distinguished from it) vs. leaving existing households permanently stuck at the old set. Instead: anyone below `CURRENT_STARTER_VERSION` who already has `starterLibrarySeeded: true` gets a **distinctly-worded "Starter Library Has Grown" prompt** (new `showUsdaGrowthOffer` state) offering just the delta — accepting calls the same `seedStarterLibrary()`, which is dedup-safe by name against the household's *full live ingredient list* (not just `DEFS`), so it can't create duplicates for anyone who separately already has some of these 339 items from another import (e.g. the JSON Import of this same source file). Declining still bumps the version, so the household isn't asked again. `migrateStarterLibrary()`/`LEGACY_FLAT_NAMES` needed no changes — that function always seeds from whatever `DEFS` currently contains, and the legacy-name list is about detecting a completely different, older data shape unrelated to this expansion.

**Verification:** `npm run build` (tsc + vite) passes with all 440 entries. Checked every "101 ingredients" reference across the codebase for staleness — user-facing: `StarterLibraryPrompt.tsx`'s own prompt copy (already dynamic via `STARTER_INGREDIENT_COUNT = DEFS.length`, no hardcoded number there) and the Help page's Starter ingredient packs bullet (had a literal "101," fixed to 440 with a new sentence about the growth-offer path). Code comments: `brandedLibrary.ts`, `JsonImportTab.tsx`, `types/index.ts`, `importNormalization.ts` all had stale "101-item" references describing the generic set — updated or generalized (some are legitimately historical narrative describing the branded-pack false-positive testing that happened when the set really was 101 items, and were left as historical fact rather than rewritten). Checked and left untouched, deliberately: `branded-starter-pack-summary.md` and `starter-library-audit.md` at the repo root — both are dated, frozen point-in-time snapshots (matching how the original `.docx` was left untouched for history), not living docs, so rewriting their "101" mentions would misrepresent what was true on the date they were written. This document's own Section 2 comparison table header *was* updated (101 → 440) since it describes current state, not a historical event. **Not live-clicked through** — no connected browser this session, so the actual prompt UI (both the first-time and growth-offer variants), the category chips, and a real seed/migrate run were not visually confirmed, only build-verified and read-verified against the code.

**Silent auto-seed error handling (fixed 2026-07-24):** the empty-install/legacy-migration `useEffect` this section runs in had no try/catch at all — a mid-loop failure in the migration branch left a "Updating ingredient library…" toast stranded on screen forever (a real, demonstrable bug); the plain-seed branch showed no UI either way and turned out to self-heal on the next app load. Fixed with a try/catch around the whole effect and a new dismissible error toast. See "Functional Risk batch" in Section 5 for the full write-up — this fix was **not** click-verified live, since the household's real production database is already past `CURRENT_STARTER_VERSION` and can't naturally re-trigger these branches without resetting real settings flags on the live account.

**UI behavior:** when only one pack's decision is outstanding, the prompt shows that pack alone, with the exact same single-button "Load N Ingredients" / "Skip" presentation the original single-pack version always had (byte-identical trigger conditions for the USDA branch — this was a hard requirement when the second pack was added, not just a nice-to-have). When both are outstanding at once (a non-empty install that hasn't decided on either), the prompt shows two checkboxes instead (USDA defaults checked, branded defaults unchecked — it's a much bigger, single-store, more opinionated dataset) with a unified "Load Selected (N)" / "Skip" pair; clicking either button resolves both decisions at once, loading whichever boxes were checked.

## 3. Settings Page

Seven tabs (state-driven, no separate routes), deep-linkable via `?section=` query param:

- **Household** — household name/size; per-person profiles (name, Simple/Complex mode, demographics, Payday Schedule).
- **Preferences** — Unit System (Imperial/Metric), Theme, Text Size (presets + 10–20pt slider), Store Preference toggle, Kitchen Reference Photos retention policy (always ask / always keep / always discard).
- **Integrations** — AI Provider dropdown + key (Anthropic/Gemini/OpenAI/Ollama), USDA key, standalone Google Gemini key + model picker (with a live "Check available models" button), Supabase URL + Anon Key.
- **Nutrients** (labeled "Optional Nutrients" in the UI) — toggles for Saturated Fat, Trans Fat, Alcohol, Water Intake, Weight Tracking; macro-history retention window (30–365 days, default 90).
- **Ingredients** — Nutriscore/Nova/allergen badge display toggles; Allergen Watch List (which of the 12 tracked allergens actually trigger a meal-plan warning).
- **Lists** (labeled "Lists Management") — free-form management of ingredient categories, recipe tags (grouped), brands, and stores, with Levenshtein-distance fuzzy-duplicate warnings.
- **Data** — Cloud Sync (Section 11), three-tier Export, Import with conflict handling, and granular per-category Reset.

**Layout note (2026-07-22):** the page is bounded and centered at a 1280px max-width (`.page`), and each tab's ~640px-capped form content is centered within its content pane (`align-items: center` on `.content`) rather than left-aligned — fixes dead space that used to strand itself on the right side only at wide viewports. See Section 14 changelog.

**Reset is still protected** — every reset action requires an explicit confirmation step. Options: reset individual categories, multiple selected categories, or everything.

**Reset is genuinely atomic (since 2026-07-24).** `performReset()` clears every target IndexedDB store inside one shared `db.transaction(stores, 'readwrite')` rather than N independent sequential `.clear()` calls — if any store's clear fails, the whole transaction aborts and rolls back, including stores already cleared earlier in that same call, so a partial reset (some stores cleared, some not) cannot happen. On failure, a specific error message is shown (reusing the same result/error modal Import already used) stating that nothing was changed; both buttons in the confirmation dialog disable and the Reset button reads "Resetting…" while in flight, so the UI never looks silently stuck. Empirically confirmed with a real IndexedDB implementation (not just reasoned about): forcing an abort mid-transaction after one store had already been cleared left that store's data fully intact afterward. Before this fix, the loop had no error handling of any kind.

**Import (backup restore) is now genuinely atomic too (since 2026-07-24).** `executeImport()` previously ran each of the 7 backup-restore data types as its own independent transaction, with nothing tying them together — a failure partway through left earlier types already committed while the outer error message implied total failure. Rewritten to use one shared transaction spanning all 7 stores, matching `performReset()`'s pattern exactly, with the skip-strategy duplicate check reading through that same transaction. Empirically verified (62/62 checks, `fake-indexeddb`, forced failure after each of the 7 store types individually) and click-verified live in production: a real throwaway backup file was imported twice against the real household database — once landing cleanly, once correctly detected and skipped as a duplicate — with the ingredient count confirmed back to baseline afterward. See "Functional Risk batch" in Section 5 for the full write-up.

## 4. Ingredient Database

The backbone of the app — every recipe, macro calculation, and grocery list traces back here. `IndexedDB` store `ingredients`.

**Structure:** a parent `Ingredient` (e.g., Ketchup) holds one or more brand `IngredientVariant`s underneath (Heinz, Hunt's, Store Brand), each with its own macros, cost, and serving info.

**Per-variant fields:** brand, default unit, serving size/unit, macros, package cost + total servings in package (app auto-calculates cost per serving, stamps `priceLastUpdated` whenever cost changes), USDA FDC ID, barcode, Nutriscore grade (A–E), Nova group (1–4), allergen flags, optional store/notes.

**Toggles:** Perishable (with a Frozen sub-toggle), Always On Hand (excluded from grocery lists by default), Archive (soft-hide, preserves recipe references) vs. permanent Delete.

**Category system:** 21 user-manageable categories (expanded from an original 15 via a one-time migration). Search by name; filter by category, Nutriscore, Nova group, allergen contains/excludes, and archived status.

**Merging duplicate ingredients (added 2026-07-24, made atomic 2026-07-24):** `mergeIngredients(keepId, mergeAwayId)` in `src/db/mergeIngredients.ts` is a shared, general-purpose capability — not tied to any one duplicate source (barcode leading-zero bugs, JSON Import collisions, Receipt Scanner, manual double-entry, the branded starter pack all produce the same underlying problem: two ingredient records that are really one product). It's a straight one-for-one replacement, no parent/child or multi-variant merge: every reference to `mergeAwayId` is repointed to `keepId`, then `mergeAwayId` is deleted. **Genuinely atomic**: every read and write — recipe repointing, grocery-list repointing, macro-log repointing, category reconciliation, and the final deletion — runs inside one shared `db.transaction(['ingredients','recipes','groceryLists','macroLogs'], 'readwrite')`, the same pattern already established by `applyReceiptSaveBatch()` (Receipt Scanner) and `performReset()` (Settings → Data → Reset). If anything throws, the whole transaction aborts and rolls back everything already written in that call, including repoints that had "succeeded" moments earlier in the same run. This closed a real, previously-flagged gap: an interruption after deletion but before category reconciliation used to leave the category permanently stuck (retrying threw immediately since the merge-away record no longer existed) — that state can no longer occur, since deletion and reconciliation now either both commit or neither does.

*Every place an ingredient id can be referenced, confirmed against the actual data model (`src/types/index.ts`, `src/db/schema.ts`) before writing the repointing logic — not assumed:*
- **Recipes** (`Recipe.ingredients[].ingredientId` / `.variantId`) — repointed. ✅ existing behavior for `.ingredientId`.
- **Grocery lists** (`GroceryItem.ingredientId` / `.variantId`, inside `items[]`/`manualItems[]`/`remainderItems[]`, every list regardless of status) — repointed. **This was a real gap — no repointing existed for grocery lists anywhere in the app before this.**
- **Macro logs** (`MacroLogEntry.variantId` — this type has no `ingredientId` field at all) — repointed defensively. Checked every write path in the app: this field isn't actually populated by anything today, but it's part of the persisted schema, so it isn't assumed safe to skip.
- **Meal plan days/templates** — confirmed these only ever hold a `recipeId` (via `MealSlotItem`), never a direct ingredient reference — repointing recipes covers them transitively, no separate handling needed.
- **Recipe collections** — only hold `recipeIds`, no ingredient reference.
- **Household items, kitchen references, processed receipts, settings** — unrelated entities, confirmed no ingredient reference.
- **Not touched, deliberately:** `src/utils/recentlyLinked.ts`'s device-local "recently linked" list (`localStorage`, capped at 10 entries) — a UI convenience, not persisted app data, and it ages out on its own.

Because this is a straight one-for-one replacement (no variant-matching feature), a reference that had pinned a *specific variant* of the ingredient being merged away is repointed to the **keep** ingredient's *default* variant — there's no reliable way to know which of keep's variants corresponds to the one going away without building real variant-matching, which this deliberately doesn't do. `countIngredientReferences(id)` is the read-only counterpart, used to warn before a plain delete (which does **not** repoint anything, unlike merge) with exact recipe/grocery-list/macro-log counts.

**Category reconciliation (added 2026-07-24):** `mergeIngredients()` takes an optional `MergeOptions.category` — when provided and different from the keep ingredient's current category, it's applied as the last step of the merge. Before this, a category disagreement between the two records was silently resolved by "whichever one was kept wins," with no review step — found live merging real barcode-duplicate pairs (Beef Broth: Meat & Poultry vs. Soups & Broths; Whole Flax Seeds: Baking & Pantry vs. Rice & Grains — see `TEST_FIXTURES.md`). Both merge UIs now show a simple dropdown, but **only when the two records actually disagree** — hidden entirely when categories already match, so the common case stays a single click.

**Two entry points, one implementation:**
- **Dev Tools → Barcode Duplicate Finder**: each candidate pair gets a "Keep" radio (defaults to whichever entry has the *longer* raw barcode string — directly matches the leading-zero bug's own signature, since the intact 13-digit code is the more complete/original one), a **Merge into "…"** button per non-keep entry, a per-entry **Delete** (with the reference-check warning), and a group-level **Skip this pair** (session-only dismissal — reappears on a later scan, nothing is persisted, so a skip can never silently hide a real duplicate forever). A category-conflict dropdown appears per group when the entries disagree.
- **Ingredients page → "Merge…" button** on every ingredient card: opens `MergeIngredientModal`, search for the other ingredient (reuses the existing `IngredientPicker`), then a side-by-side compare with a Keep radio (defaults to the card you started from) showing both ingredients' reference counts before you confirm, plus the category dropdown when needed. For duplicates that have nothing to do with barcodes at all — manually-typed double-entries, two separate imports of the same name.

**Related gap, fixed 2026-07-24 — see the full write-up below.** `src/db/supabase.ts`'s `resolveIngredientDuplicate()`, used when Cloud Sync detects a name collision between a local and cloud ingredient, previously only repointed `Recipe.ingredients[].ingredientId` (via a private `repointIngredientId()`) — never `.variantId`, never grocery lists, never macro logs. It now reuses `mergeIngredients()`'s own reference-discovery logic directly, extracted into a shared helper, and runs atomically. The "cloud-side id may never have been saved locally" precondition that originally blocked reusing `mergeIngredients()` here was investigated in full and turned out not to block a shared implementation once the repointing logic was extracted at the right level of abstraction — see "Cloud Sync duplicate resolution — reference integrity" in this section.

**Verification status for the merge feature:** `npm run build` (tsc + vite) passes. The core repointing logic was originally verified against realistic mock data covering recipes (with and without a pinned variant, plus an unrelated and an unlinked row), all three grocery-list item buckets, macro logs, and the self-merge/missing-ingredient guard clauses — 16/16 checks passed. **It has since been confirmed working end-to-end against real production data, done by the user directly**: all 8 real leading-zero duplicate pairs found in the live household database (see `TEST_FIXTURES.md` for the last 3, captured before merging) were resolved via the Barcode Duplicate Finder's Merge action — a fresh scan afterward showed 0 remaining pairs, and each discarded ingredient was confirmed actually gone from the Ingredients list.

**Atomicity fix verification (2026-07-24):** the transaction rewrite was empirically verified — not just reasoned about — using a real spec-compliant IndexedDB implementation (`fake-indexeddb`, installed temporarily via `--no-save`, never added to `package.json`, removed after) driven through the same `idb` wrapper the app uses. The happy path (all 4 stores correctly updated) plus 4 separately forced failure points (after recipe repointing, after grocery-list repointing, after macro-log repointing, and immediately after the final delete) were each tested — in every forced-failure case, every write already issued in that same transaction rolled back completely, leaving the database byte-identical to its pre-merge state. 20/20 checks passed. This also surfaced and fixed a real (minor) unhandled-promise-rejection edge case in the `tx.abort()` catch pattern — see the 2.16 changelog entry. Build-verified; deployed; confirmed live via byte-identical MD5 hashes of all 3 local build chunks containing the merge code (main bundle, `IngredientsPage-*.js`, `DevToolsPage-*.js`) against the fetched production chunks.

**Click-verified live in production (2026-07-24) — the first of this session's atomicity fixes actually driven through a real browser end-to-end**, unlike the barcode-consolidation and `performReset()` fixes earlier the same day (both still only logic-verified). Two throwaway test ingredients were created directly in the live household database via the real Ingredients UI ("ZZZ TEST MERGE KEEP" / Meat & Poultry, "ZZZ TEST MERGE AWAY" / Soups & Broths — deliberately different categories to exercise reconciliation), merged via the real "Merge…" button including the category-disagreement picker (picked "Soups & Broths," not the default, to prove the picked value actually wins), and the result was confirmed directly: "Merge Complete" showed correct 0/0/0 reference counts, the merged-away ingredient was gone, and the surviving ingredient's category had genuinely changed to the picked value. ### Cloud Sync duplicate resolution — reference integrity (fixed 2026-07-24)

`resolveIngredientDuplicate()` (`src/db/supabase.ts`) is what runs when the user clicks Keep Mine / Keep Theirs / Keep Both on a Cloud Sync name-collision (see Section 11) — a genuinely different trigger from `mergeIngredients()` above (explicit per-conflict user choice during sync review, not a general-purpose "these are the same product" merge), but it discards one ingredient id in favor of another the same way, and had the same reference-repointing gap `mergeIngredients()` was fixed to close: it only ever updated `Recipe.ingredients[].ingredientId`, never `.variantId`, grocery lists, or macro logs.

**Precondition investigated before writing any fix code, as explicitly required.** `mergeIngredients()` requires both ids to already exist as local `Ingredient` records — it reads both via `ingredientStore.get()` and throws if either is missing. Cloud Sync's situation is different: traced through `syncIngredients()`'s actual duplicate-detection code (both the push-side `cloudNameMap` check and the pull-side `localNameMap` check) and confirmed as a hard invariant, not a maybe — whenever a name collision is detected, the colliding cloud-side record is *deliberately withheld* from `saveIngredient()`, specifically so it routes to manual review instead of silently creating a duplicate. There is no code path in this app where a `SyncDuplicate.cloudItem` was already saved locally at the time it's flagged.

**The answer is a hybrid of the offered options, direction-dependent — not one blanket answer:**
- **keep-cloud** (discard local, keep cloud's version): `saveIngredient(cloud)` already ran — in both the old code and the new — *before* any repointing happens. By the time repointing runs, `cloud.id` genuinely exists as a local record, satisfying `mergeIngredients()`'s own precondition in full, just established one statement earlier than in a plain merge. This is also where the *real* bug lived: `local.id` (the repoint source) is an already-established local ingredient that can have real recipe/grocery/macro-log references, exactly like a normal merge's `mergeAwayId`.
- **keep-local** (discard cloud, keep local's version): `cloud.id` is *never* saved locally at any point in this flow. But a local reference to it is structurally impossible regardless — every place an ingredient id gets attached to a recipe line, grocery item, or macro log is set via `IngredientPicker`, which sources its options exclusively from `getAllIngredients()` (local records only). There is no UI path in the app that could ever link something locally to an id that was never itself a local `Ingredient`. So for this direction specifically, the "never existed locally" precondition is real but does not create an actual reference-integrity gap — repointing FROM `cloud.id` is a structurally guaranteed no-op.

**Fix — one shared implementation, not a second parallel one.** `mergeIngredients()`'s reference-discovery/repointing logic was extracted into a new function, `repointIngredientReferences()` (`src/db/mergeIngredients.ts`), which both `mergeIngredients()` and the rewritten `resolveIngredientDuplicate()` now call. The key design choice that makes this work for both directions: the helper operates on an already-open transaction's store handles plus the two ids and their variant-id sets, passed in directly — it never looks up the "from" id in the ingredients store itself. That's what lets it work correctly for keep-local's structurally-never-local case without any special-casing: it's given `cloud.id` and `cloud.variants` straight from the in-memory `SyncDuplicate` object (no DB read needed), searches recipes/grocery lists/macro logs for literal matches, and — as the precondition analysis predicted — finds zero, safely. `mergeIngredients()` itself was refactored to call this same helper (pure extraction, same behavior, now delegates instead of inlining the loops) rather than left untouched while a second copy was written elsewhere.

**Atomicity.** The keep-cloud direction (save cloud + repoint + delete local) now runs inside one shared `db.transaction(['ingredients','recipes','groceryLists','macroLogs'], 'readwrite')`, matching `mergeIngredients()`/`applyReceiptSaveBatch()`/`performReset()`'s established pattern — either the whole local resolution commits or none of it does. Keep-local's repoint (a proven no-op) still runs inside the same transaction shape, for defensive consistency rather than being skipped outright — if the "never local" invariant is ever violated by some future change, this closes the gap instead of silently assuming it can't happen. **One genuine, structural limitation, not a shortcut**: the remote Supabase upsert/delete calls (used only by keep-local, to push the kept local record up and retire the cloud's old row) happen *after* the local IndexedDB transaction commits, as a separate step — a browser IndexedDB transaction cannot span a network call, full stop, so this can't be folded into the same atomic unit no matter how it's written. If the local resolution succeeds but the network call then fails, the local data is already correct and is the source of truth going forward; the stale cloud row will simply be reconciled again (flagged as a duplicate once more) on the next sync rather than silently lost.

**`CloudSyncSection.tsx` also previously had zero error handling around any of this** — `handleResolveDuplicate()` awaited `resolveIngredientDuplicate()`/`resolveRecipeDuplicate()` with no try/catch at all; a throw would have surfaced as a completely silent unhandled promise rejection. Fixed alongside: a `resolving`/`resolveError` state pair, buttons disabled and relabeled "Resolving…" while in flight, a visible error message in the modal on failure (matching the standard set by `MergeIngredientModal.tsx`/`DevToolsPage.tsx`'s merge error handling), and the modal now stays open on failure instead of vanishing either way. The bulk-resolve path (`makeBulkResolver`) now catches per-item failures individually — one bad duplicate no longer aborts resolving the rest of the batch, and failures are appended to the existing `summary.errors` list (the same mechanism `SyncResultDisplay` already renders errors through) rather than added as a second, parallel error surface.

## 5. Ingredient Import Methods

*(New section vs. the original design doc — this grew into seven distinct import paths, all funneling through review before anything saves.)*

Seven tabs on the Import Ingredients page: **Barcode Lookup, USDA Lookup, Gemini Lookup, Scan Label, Receipt Scanner, Bulk Entry, JSON Import.** Barcode/USDA/Gemini/Scan Label all route through a shared `ReviewScreen` before saving — nothing auto-saves. Across all seven, saving always requires an explicit user action.

- **Barcode Lookup** — checks local DB first, then Open Food Facts; optional Gemini enrichment fallback if OFF has zero macros.
- **USDA Lookup** — batch search by name, no AI.
- **Gemini Lookup** — AI-driven lookup by product name/brand; requires a Gemini key.
- **Scan Label** — photograph a nutrition-facts panel; AI reads it; low-confidence fields are highlighted for manual review.
- **Receipt Scanner** — photograph a grocery receipt; per-line price/quantity parsing (deterministic math, not AI arithmetic) + barcode-first/name-fallback ingredient matching with confidence tiers; three-way per-line choice (Add as Ingredient / Add as Household Item / Don't Add); a nutrition fallback chain (auto barcode lookup → photograph the product label → on-demand Gemini web search with independently-verified confidence) fills in nutrition for brand-new items created this way. Full behavior detailed below — this is a substantially deeper feature than the one-line summary suggests.
- **Bulk Entry** — manual spreadsheet-style table, no AI.
- **JSON Import** — accepts this app's own export format or an Open Food Facts bulk-converter format; three import modes (Add New Only / Add + Update Existing / Replace).

### Receipt Scanner — detail

*(Verified 2026-07-24 directly against the code — this subsection replaced a one-sentence summary that undersold how much real logic is here.)* Files: `ReceiptScannerTab.tsx` (capture/stage flow), `ReceiptLineReview.tsx` (bulk review + save), `receiptMatching.ts` (matching), `receiptPriceNormalization.ts` (price/quantity parsing), `barcodeValidation.ts` (checksum), `db/processedReceipts.ts` (duplicate detection).

**Identification priority — barcode first, name second, in that strict order.** Any numeric code Gemini reads next to a line is tried as a real barcode before anything else: `barcodeLookupCandidates()` expands it to both the raw digits and its UPC-A ↔ EAN-13 leading-zero equivalent, and each candidate must pass real checksum validation (see below) before being trusted at all — a barcode-shaped string that fails checksum is discarded, never used as identity. A checksum-valid barcode is matched against every ingredient's `variant.barcode` (exact string, all matches collected — not just the first, so a shared-barcode data problem can be caught). A hit here is `tier: 'high'`, auto-selected, and per the code's own comment, "barcode identity always wins over fuzzy name matching and is never overridden by it." Only when no barcode was present, or none of its candidates validated or matched, does the scanner fall back to `findSmartMatches()` (the same name-matching primitive `ReviewScreen.tsx` uses elsewhere in the app) against the AI-parsed item name — multiple hits are re-ordered (brand-mentioned-in-receipt-text first) and capped at 5 candidates, tiered `'high'` for exactly one match or `'medium'` for more than one; medium is never auto-selected.

**Barcode checksum validation — real, not cosmetic.** `isValidBarcodeChecksum()` implements the actual UPC-A (12-digit)/EAN-13 (13-digit) mod-10 check-digit algorithm, not a length or pattern guess. A misread barcode digit fails this and is dropped before it can reach matching.

**Barcode vs. name disagreement — surfaced to the user, not algorithmically "resolved."** When a checksum-valid barcode matches an ingredient, the scanner separately runs `findSmartMatches()` against that same line's parsed name. If the name search doesn't also turn up the barcode-matched ingredient, `barcodeTextDisagreement: true` is set and shown in review — but the barcode match still wins and is still what gets auto-selected; there is no vote or scoring between the two signals, only a flag for a human to notice a possibly-wrong barcode read. Separately, if a barcode matches *more than one* ingredient record (a data-integrity edge case), `barcodeMultiMatch: true` drops the tier to `'medium'` and shows all matches as candidates instead of auto-picking one.

**Staged/atomic approval workflow — real, fully atomic since 2026-07-24.** Nothing writes to the database while lines are parsed or matched — `ReceiptLineReview.tsx` holds every line in local state, independently editable and independently validated (servings > 0, unit price > 0, a name if creating new, a resolved match/Create-New choice, a resolved price decision). Saving only happens on **Save All**. Every write for the batch — *ingredient* ops (`updatePrice` / `addVariant` / `createIngredient`), household-item rows, and the processed-receipt record — goes through `applyReceiptSaveBatch()` as one IndexedDB transaction spanning the `ingredients`, `householdItems`, and `processedReceipts` stores: either the whole Save All lands or none of it does. (Prior to 2026-07-24, only the ingredient ops were atomic — `applyIngredientBatch()` transacted `ingredients` alone, and household items were saved individually in a separate loop right after, so a failure partway through that loop could leave ingredients committed but household items missing. Closed by folding all three stores into one transaction.) Already-saved rows are skipped on a retry, so a partial failure can be re-submitted without double-writing what already landed.

**Duplicate receipt detection — real, and a soft warning, not a hard block.** `findMatchingProcessedReceipt(store, date, total)` checks the newly-parsed receipt's store (trimmed/lowercased), date (exact match), and total (within $0.01, for rounding) against every previously-saved `processedReceipts` record, immediately after Gemini parses the photo and before review even opens. If store, date, or total is missing, the check is skipped — no warning is possible for a receipt Gemini couldn't fully read. A hit shows a dedicated screen ("This looks like a receipt you've already processed...") with **Cancel** or **Proceed Anyway**; proceeding continues straight into normal review, so nothing is actually blocked, only flagged. Crucially, a `processedReceipts` row is only written at the end of a *successful* Save All — scanning a receipt and abandoning the review leaves no record, so it won't trigger the warning on a later re-scan.

**Sale/discount detection — real, exactly the ">10%" pattern.** `priceDeltaInfo()` computes `pct = |newPrice − oldPrice| / oldPrice` and flags `isSaleRange` at `pct >= 0.10`. It only appears when a line is matched to an existing variant that already has a different `packageCost`. Below 10%, the prompt is a plain "Update?" (Update price / Keep old price). At 10%+, the box is visually flagged and reworded to "...this could be a sale," offering **Update baseline price** or **This was a sale — don't update**. Choosing the sale option (`priceDecision: 'sale-skip'`) still marks the row saved but queues no price-update op — the existing price is left untouched. Nothing about the flagged sale price is logged anywhere; it's a same-session prompt only, not a price-history feature.

**"High confidence" match-provenance labeling — investigated and fixed 2026-07-25.** This was tracked as an open item after the Functional Risk batch review (2026-07-24) reclassified it out of that batch as a labeling/match-provenance question rather than a save-loop issue. A fresh investigation — re-tracing the actual code rather than trusting the prior conclusion — found the prior claim was **partially wrong**: `git blame` traced the header badge's `line.match.barcodeMatch ? 'Barcode match' : TIER_LABEL[line.match.tier]` logic (`ReceiptLineReview.tsx`) back to the very first commit that added Receipt Scanner (`ee0af0c`) — a barcode match and a lone name match have **never** rendered identical badge text; match provenance (`RankedCandidate.source: 'barcode' | 'name'`) does reach the UI and is used correctly both in that header badge and in the per-candidate "barcode"/"name match" tags shown in the picker list.

The real, still-live problem sat one level deeper: `findSmartMatches()` (`smartDuplicate.ts`) is a flat pass/fail with no internal reason code — exact-string equality, close edit-distance (≤2), and one-directional keyword-subset matches (e.g. "Lime" matching "Key Lime Pie Filling" purely because both contain "lime") all collapse into the same boolean result, so any *lone* match from any of those three signals got `tier: 'high'` identically. That tier isn't just a badge color: `ReceiptScannerTab.tsx` uses `tier === 'high'` to auto-select the candidate into `mode: 'match'` and pre-run `resolveCandidateSelection()`, and when the matched variant's stored price doesn't conflict with the receipt's price, the resulting `priceDecision` is `'not-needed'` — a value `validateLine()` never blocks on. A false-positive fuzzy guess could therefore be silently written by "Save All" with zero required clicks, under a green "High confidence" badge visually identical in color (`tier_high`, `color-mix` with `--color-success`) to an actual barcode match. Classified as **misleading**, and a real functional risk, not a cosmetic wording issue.

**Fix**: `matchLine()` now only assigns `tier: 'high'` to a lone name match when it's a genuine exact-name match (the matched ingredient's name, trimmed and lowercased, equals the receipt line's parsed name); a lone match reached only via edit-distance or keyword-subset now gets `tier: 'medium'`, routing it through the exact same "Pick a match" human-review path — forced candidate list, nothing pre-selected, `mode: 'pending'` — already used for every other ambiguous line. No new UI component was built. Options considered and rejected: explanatory text alone or a new badge/visual system (neither closes the actual auto-select/zero-click-save gap, only re-describes or re-colors it); a second independent "data completeness" confidence dimension (no real signal exists to back one at match time); reusing ReviewScreen's side-by-side compare card (that pattern fits ReviewScreen's single-item flow — Receipt Scanner is bulk/multi-line by design, and its existing lightweight candidate-list + source-tag pattern is the proportionate equivalent, already built, just not previously reached by the lone-fuzzy case). **Verified**: 12/12 checks in a byte-faithful port of the real `editDistance`/`keywords`/`findSmartMatches`/`matchLine` logic (copied verbatim from the current files), covering all 4 required match paths against realistic catalog fixtures — barcode single-hit, exact-name lone match ("SPANISH RICE"), fuzzy-name lone match ("Lime" → "Key Lime Pie Filling," the real risk case), and multi-candidate ("Rice" → 3 candidates) — plus a downstream check proving the old `mode: 'match'` (auto-selected) becomes the new `mode: 'pending'` (blocked pending an explicit pick) for the fuzzy-lone case, with the exact-name and multi-candidate paths unchanged. A direct import of the real TS module was attempted first (Node 24 has native TS stripping) but blocked on extensionless relative imports that only Vite's resolver, not Node's ESM loader, can follow. Build-verified. **Not click-verified live**: reproducing this exact scenario through the real workflow needs a photographed receipt whose Gemini OCR text happens to fuzzy-match exactly one real household ingredient by keyword-subset (not exact name) — not reliably constructible without fabricating a receipt image or risking an unintended write against real production data if the scenario didn't land as designed; deliberately skipped, same judgment applied to StarterLibraryPrompt's skipped live test. Files changed: `src/utils/receiptMatching.ts` only.

**Matching code reuse — partial, not the shared `findIngredientMatch()` pipeline.** Receipt Scanner does **not** use `findIngredientMatch()` / `importNormalization.ts` — confirmed neither is imported anywhere in the Receipt Scanner files; that function is used only by JSON Import and the branded starter-pack seed (see the 2.2 changelog entry). Receipt Scanner has its own `receiptMatching.ts`, which reuses `findSmartMatches()` directly from `smartDuplicate.ts` for name matching. **Barcode matching, however, is fully shared as of 2026-07-24** — `receiptMatching.ts` no longer has its own private `findAllBarcodeMatches()`; it imports `findAllBarcodeMatches()`/`findMatchingVariant()` from `smartDuplicate.ts`, the same functions `findIngredientByBarcode()` and `ReviewScreen.tsx` now use too. Receipt Scanner still needs *every* ingredient sharing a barcode (to detect `barcodeMultiMatch`), which is exactly what the shared `findAllBarcodeMatches()` returns — no behavior change was needed for Receipt Scanner itself, only a routing change. See "Barcode comparison — one shared implementation app-wide" below and the 2.14 changelog entry.

### Barcode comparison — one shared implementation app-wide (since 2026-07-24)

Before this fix, barcode matching was implemented four separate times with inconsistent behavior: `findBarcodeMatch()`/`findAllBarcodeMatches()` (`smartDuplicate.ts`), `findIngredientByBarcode()` (`db/ingredients.ts`), `ReviewScreen.tsx`'s inline check, and Receipt Scanner's own private `findAllBarcodeMatches()` in `receiptMatching.ts`. Only Receipt Scanner did checksum validation and leading-zero normalization; the other three were plain `===` string comparison, meaning the already-fixed leading-zero duplicate bug (Ingredient Converter v5, see Section 15) could still be reproduced through barcode lookup, scanning, manual entry, or ReviewScreen's dedup check — a barcode stored pre-v5-fix without its leading zero would never match a fresh, correctly-formatted scan of the same physical product.

`smartDuplicate.ts` is now the single authoritative source for barcode comparison everywhere: `findBarcodeMatch()`, `findAllBarcodeMatches()`, and the new `findMatchingVariant()` (given a barcode and an already-matched ingredient, finds which specific variant actually carries the matching barcode). All three use the same two-tier strategy: (1) exact string match first, unconditionally — preserves existing behavior for anything already in the database, checksum-valid or not, so there is zero regression risk for barcodes already working today; (2) only if no exact match, expand to checksum-valid UPC-A/EAN-13 leading-zero-equivalent candidates via the existing `barcodeLookupCandidates()`/`isValidBarcodeChecksum()` pipeline (`barcodeValidation.ts`, previously used only by Receipt Scanner) and try those. `findIngredientByBarcode()` and `ReviewScreen.tsx`'s inline check now both call the shared `findBarcodeMatch()`/`findMatchingVariant()` instead of doing their own comparison; Receipt Scanner's `matchLine()` now imports the shared `findAllBarcodeMatches()`/`findMatchingVariant()` instead of its own private copy.

### Functional Risk batch — import/save-loop error handling (investigated and resolved 2026-07-24)

A prior audit batched 5 items under one "missing error handling around per-item save loops" theory. ## 11. Cloud Sync, Household Sync Code, Family Share & Account Sign-In

*(Fully built. The original design doc listed this under "Intentionally Left for Later" — that's no longer accurate as of this rewrite.)*

Core engine: `src/db/supabase.ts`. UI: Settings → Data → Cloud Sync.

### Two layers, deliberately separable
1. **Account sign-in** (added 2026-07-21/22, `AccountSection.tsx`) — real per-user Supabase Auth (email + password). Sign up/in/out; create or join a **household** by code; owner-only member role management (owner/contributor/readonly). This is the recommended path for a new setup.
2. **Household Sync Code** — the older mechanism: a shared human-memorable string (e.g. `adjective-noun-1234`). Still works fully standalone without ever signing in — creating a household via Account sign-in just auto-fills this code for you. Historically this code alone was the *entire* access model (a plaintext string checked with wide-open `using (true)` RLS policies); the Account layer adds real per-user access control on top without removing the old path.

### What syncs
Eight cloud tables, everything scoped by household code: ingredients, recipes, meal plans, grocery lists, household items, collections, kitchen references, and a curated subset of settings (`sync_settings`). **Never synced:** all API keys, device theme/text-size preferences, the sync credentials themselves, one-time migration flags, `cloudSyncPromptDismissed`, and — deliberately — **macro logs and weight history**, which stay entirely device-local/personal.

### Push/pull mechanics
Full-state fetch before push or pull (paginated, handles large households); duplicate-safe in both directions (checks same-name-different-id before creating a second row); three-way conflict resolution (Keep Mine / Keep Both / Keep Theirs — note Keep Both doesn't repoint recipe references the way the other two do); newest-`updated_at`-wins merge for non-duplicate conflicts. **Entirely manual/button-triggered** — no background sync, no sync-on-load. The only automatic Supabase traffic is a once-per-23-hours no-op keep-alive ping to stop the free tier from auto-pausing.

**Found live, 2026-07-25:** a real sync of 6,290 items gave no progress feedback beyond the button greying out — looked indistinguishable from stuck/broken for 5+ minutes before DevTools confirmed hundreds of successful requests in flight. Cloud Sync was designated the **flagship implementation** of `OPERATION_FEEDBACK_STANDARD.md` (repo root) — the shared status/progress pattern meant to unify feedback across all five of the app's long-running operations — as Phase 1 of its rollout (see `OPEN_ITEMS.md`). A separate, lower-priority finding from the same sync — pushing ingredients one row at a time (851+ sequential requests) rather than in bulk — is a distinct performance question, explicitly not part of that standard.

**Phase 1 — built and live-verified, same day.** `OperationStatus` (`src/components/ui/OperationStatus.tsx`) is a genuinely reusable component, not a Cloud-Sync-specific one that later phases would have to rebuild — it owns the standard's timing/escalation logic internally (30s/1min tiers, 60s+ stuck detection, success auto-dismiss) so a future caller only ever reports `state`/`progress`/`doneMessage`/`errorMessage`. Wired into `runSync()` and every sub-store sync function via an optional `onProgress` callback, threaded through without touching any existing error-handling or return shape — a real count/step update fires after every network request. `CloudSyncSection.tsx` flips to Working synchronously on click, before any `await`, and resolves to Done or Failed off `summary.errors`, matching existing behavior exactly. Family Share sync is deliberately untouched (out of Cloud-Sync-only scope for this phase) — `SyncResultDisplay` gained a `showSummary` prop, defaulted `true` (Family Share, unchanged) and set `false` for Household Sync (where `OperationStatus` now owns that text), so nothing renders twice. **Click-verified live against a real full sync** of the real household's 6,246 ingredients: immediate "Checking ingredients…" on click, item count climbing live and confirmed genuinely live by re-reading it across the run (638 → 1,006 → 2,198 → 3,359 → 4,460 → 5,523 → 6,004 → done) with a real progress bar, the 60s+ reassurance line appearing with the exact custom wording configured, a clean Done state ("0 new items added from cloud, 6290 items uploaded, 0 updated to newer version") with a working dismiss button, "Last synced" updating to "just now", and the success banner auto-dismissing on its own after ~5 seconds. Zero console errors. One real deployment gotcha hit and resolved during verification, worth remembering for future live checks on a long-lived tab: the first attempt showed nothing at all, traced to a stale service-worker cache on the already-open production tab rather than a real bug — a hard reload (`Ctrl+Shift+R`) picked up the new deploy and the retry worked correctly. **Not click-verified this session**: the Failed-state visual (would require deliberately breaking a real production sync) and the "taking longer than expected" stuck-state (never triggered — the real sync kept progressing) — both covered by 13/13 pure-logic checks and code review instead.

### Family Share
A second mode of the same engine (same UI card group) for sharing with family in a different home: separate `familyShareCode` (partitioned as `<code>:family`, never collides with household data), syncs **only recipes and ingredients** (cost fields stripped before upload — the point is not exposing your prices/stores), with an owner/contributor/readonly role system enforced before any network call for readonly.

### Setup — self-service now fully wired (fixed 2026-07-22)

### Outstanding security note
Every data-table RLS policy still includes a bridge clause (`household_code = the literal current code OR real membership`), so the pre-auth vulnerability (anon key + code = full read/write access) is **not yet closed** for the household actually running this app. Closing it ("Phase 3" — dropping the bridge clause) is a deliberate later step. **A full RLS audit (below, 2026-07-25) found Phase 3 should NOT run yet** — not because the policy design is unsound, but because of a specific, unresolved data risk the audit traced concretely.

### Supabase RLS security audit (2026-07-25, pre-Phase-3 verification)

**Source of truth.** No `supabase/migrations/` directory or `.sql` files exist anywhere in the repo. However, `src/db/supabase.ts` contains 5 literal SQL constants — `SUPABASE_SETUP_SQL`, `AUTH_MIGRATION_SQL`, `AUTH_MIGRATION_FIX_SQL`, `AUTH_MIGRATION_FIX2_SQL`, `AUTH_MIGRATION_FIX3_SQL` — which are the actual scripts shown to the user in the app's own "Show setup SQL" UI (`CloudSyncSection.tsx`), each with a header comment describing a specific real bug it fixes (a recursion error, a missing grant, an ambiguous-column error), all caught during an actual disposable-account live test pass per those comments and this document's own changelog — not speculative design notes. Used as primary evidence for the full inventory below; cross-checked against `src/hooks/useIsHouseholdOwner.ts`'s code comments (which quote exact casing values from a live finding) and this section's existing content.

**Full policy inventory (verbatim, current-intended state per `AUTH_MIGRATION_FIX_SQL`, which supersedes `AUTH_MIGRATION_SQL`'s original recursive policies).** 10 tables total, all RLS-enabled:

- **`households`** — one policy: `for select using (is_household_member(id))`. No INSERT/UPDATE/DELETE policy for `authenticated`/`anon` — RLS-enabled-with-no-matching-policy default-denies those commands; creation is RPC-only (`create_household`).
- **`household_members`** — `for select using (is_household_member(household_id))` (every member, including `readonly`, sees the **full** member list of their household — not just their own row); `for update using (is_household_owner(household_id))`; `for delete using (is_household_owner(household_id) or user_id = auth.uid())`. No INSERT policy — the script's own comment confirms this is deliberate: *"the two functions below are the ONLY way to create a household or join one."*
- **The 8 data tables** (`ingredients`, `recipes`, `meal_plans`, `grocery_lists`, `household_items`, `collections`, `kitchen_references`, `sync_settings`) — identical 4-policy shape per table, e.g. for `ingredients`:
  ```sql
  create policy "select: legacy code or member" on ingredients
    for select using (
      household_code = 'Angelo-family-2026'
      or is_member_of_code(household_code)
    );
  -- insert/update/delete: identical shape, using is_writable_member_of_code()
  -- (same OR structure, requiring role != 'readonly')
  ```

Client code (verified by grepping every `.from(...)` call and every table-name array passed to the generic sync helpers) only ever queries these exact 10 tables — no evidence of an 11th table in use without a policy. **Residual unknown, flagged not assumed**: an orphaned table created directly via the Supabase dashboard that the client never queries wouldn't appear in this trace — see the live-query request below.

**Function bodies, verbatim:**
```sql
create or replace function is_member_of_code(p_code text)
returns boolean language sql security definer set search_path = public stable
as $$
  select exists (
    select 1 from households h
    join household_members hm on hm.household_id = h.id
    where h.code = p_code and hm.user_id = auth.uid()
  );
$$;
-- is_writable_member_of_code() is identical plus `and hm.role != 'readonly'`
```
Both `SECURITY DEFINER` — the documented, standard Postgres pattern to avoid the exact self-referential-RLS recursion bug (`42P17`) `AUTH_MIGRATION_FIX_SQL`'s own comment says was actually hit during live testing, not theorized. `auth.uid()` is server-derived from the JWT and cannot be spoofed by a client.

```sql
-- join_household_by_code(p_code, p_display_name): looks up households where
-- code = p_code, then inserts a household_members row for auth.uid() with
-- role 'contributor' — no owner approval step, no rate limiting in the
-- function itself. This is deliberate (the code is the credential, same
-- model as the legacy sync-code mechanism) but worth flagging: generateSyncCode()
-- produces ~900,000 combinations (10 adjectives × 10 nouns × 9000 numbers),
-- and nothing in this RPC throttles guesses.
```

**Cross-household access — the central question, traced concretely:**
1. *Direct/misconfigured-client query for another household's rows*: `is_member_of_code(row.household_code)` is evaluated per-row against `auth.uid()` regardless of how the client constructed its query — a non-member's `auth.uid()` has no `household_members` row for that household, so the check returns `false` and the row is excluded, whether the request came from the app's UI, a stale client state, or a hand-crafted API call.
2. *Misconfigured push to the wrong household_code*: `is_writable_member_of_code()` gates INSERT/UPDATE identically — a write to a household_code the user isn't a writable member of is rejected with an RLS violation, failing loudly, not silently.
3. *id-collision via `upsert(..., {onConflict:'id'})`*: `id` is a single global-namespace primary key (no per-household scoping in the key). If two households' clients ever generated the same `id`, the `ON CONFLICT DO UPDATE` path still requires the **existing** row to pass the UPDATE policy for the requesting user — a non-member fails that check, so the conflicting row can't be silently overwritten. Practically unreachable regardless: `newId()` (`src/utils/ids.ts`) is `crypto.randomUUID()`.
4. *The one real path in*: `join_household_by_code(code)` — knowing a household's code is sufficient to become a real `'contributor'`, by design, matching the legacy code-based model.

**Answer: no bypass found.** RLS enforcement doesn't depend on client behavior at any of the paths traced — the only way into another household's data is knowing its code and self-joining, which is the intended, documented model, not a flaw in the policies themselves.

**The actual Phase 3 blocker — a data-casing risk the policy design can't be blamed for.** `src/hooks/useIsHouseholdOwner.ts`'s own code comment quotes exact values from a live 2026-07-24 finding: `households.code` = `"Angelo-Family-2026"` (capital A, capital F) vs. the `household_code` actually stamped on that household's synced data rows = `"angelo-family-2026"` / `"Angelo-family-2026"` (mixed casing). The RLS bridge's hardcoded literal, read directly from the SQL, is `'Angelo-family-2026'` (capital A, **lowercase** f) — a *third* distinct casing. Tracing what this means: `is_member_of_code()` does `where h.code = p_code`, case-sensitive — for a data row whose `household_code` is the all-lowercase variant, this requires `households.code = 'angelo-family-2026'`, but `households.code` is capital-F `"Angelo-Family-2026"` — mismatch, so the **real-membership path fails for that row too**, not just the bridge. The earlier casing fix (`.trim().toLowerCase()` in `useIsHouseholdOwner.ts`) was applied **only** to the Dev-Tools-gating comparison — a pure client-side UI check — never to Cloud Sync's actual data-path filters (`fetchCloudRows`/`upsertCloudRow` still use `settings.householdSyncCode?.trim()`, no case normalization) or to the underlying data itself. Cloud Sync working today is consistent with — and likely better explained by — the bridge clause silently carrying all of this household's traffic (the bridge literal was almost certainly copied from whatever casing the real device used at migration-authoring time), **not** proof that the real-membership path independently works for this household's actual data. Dropping the bridge before confirming casing parity risks a real, self-inflicted lockout of the real household's own data — not a new leak, but a real availability break with no easy rollback once the bridge SQL is gone.

**Verdict: Phase 3 is unsafe to run right now.** The policy design itself was traced and confirmed structurally sound (see the cross-household analysis above) — this is not "policy redesign required." It's a specific, data-dependent precondition that has to be checked live before the bridge — the only thing currently possibly masking a casing mismatch — is removed.

**5 narrow read-only queries requested** (for the user to run directly in the Supabase SQL Editor and paste back — no credential sharing needed): `households.code` vs. every table's `household_code` distribution (the one that actually gates Phase 3); live `pg_policies` (cross-check against the repo SQL above); live function bodies via `pg_get_functiondef` (catch any dashboard hand-edit never reflected in the repo); a full public-schema RLS-enabled listing via `pg_class` (catch an undocumented table); live grants via `information_schema.role_table_grants` (confirm no drift beyond the one already-documented ad-hoc `service_role` grant on `ingredients` from the earlier macro-schema migration, Section 4). Exact query text is in `OPEN_ITEMS.md`'s corresponding entry.

**If a mismatch is confirmed**, Phase 3's script needs one of two additions before the bridge clause is dropped: a one-time data normalization (`update <table> set household_code = 'Angelo-Family-2026' where household_code ilike 'angelo-family-2026'`, per table) or — the more durable fix, since it doesn't depend on data staying clean forever — rewriting `is_member_of_code()`/`is_writable_member_of_code()` to compare case-insensitively (`where lower(h.code) = lower(p_code)`). No SQL was executed as part of this audit; Phase 3 was not run.

### Casing-drift remediation — executed and live-verified (2026-07-25, closes the Phase 3 blocker above)

The mismatch the audit flagged as a possibility was confirmed real via the 5 live queries, then fully investigated and remediated before any write was proposed — not fixed reactively.

**Scope, confirmed with live per-table queries.** 22 non-canonical rows across 4 of the 8 cloud tables: `ingredients` (17), `meal_plans` (3), `grocery_lists` (1), `sync_settings` (1). `recipes`, `household_items`, `collections`, `kitchen_references` were already 100% clean. Every non-canonical value reduced to a case-fold of the identical 20-character `Angelo-Family-2026` string — no unrelated household mixed in, confirmed against the live `households` table (which, separately, turned up 6 leftover disposable test households from earlier live-testing sessions — harmless, since none of their codes appear in any data table, but real un-cleaned-up residue; tracked in `OPEN_ITEMS.md`, not addressed here).

**Origin, traced from actual code rather than assumed.** Three independent, un-normalized free-text entry points exist for what's conceptually "the same" credential: the original Household Sync Code field (`CloudSyncSection.tsx`, plain `onChange`, zero transformation), and Account's Create-Household and Join-Household forms (`AccountSection.tsx`, each its own local `useState`, `.trim()` only, never pre-filled from the other). Direct evidence the real code was hand-typed rather than generated: `generateSyncCode()` always lowercases its household-name prefix and always appends an adjective-word before the number (`angelo-family-happy-4821`-shaped) — `Angelo-Family-2026` doesn't match that shape at all. Live `ingredients` timestamps confirmed the drift's actual temporal pattern precisely: two clean, non-overlapping historical clusters (`angelo-family-2026` rows 2026-06-28 21:39 → 2026-06-29 23:32; `Angelo-family-2026` rows 2026-07-18 23:44 → 2026-07-21 03:01), then a clean ~2-day gap before canonical `Angelo-Family-2026` rows begin 2026-07-22 22:13 and continue through the most recent sync — three discrete casing phases, not continuous drift, with the final cutover lining up almost exactly with `households.code`'s own creation timestamp (2026-07-23T00:15).

**`sync_settings`'s stale row required its own analysis, not a blind recolor.** Its primary key is derived from the code itself (`const rowId = `${code}:settings``, `db/supabase.ts:1013`) — unlike the other 7 tables, where `id` is the item's own `crypto.randomUUID()`, independent of `household_code`. Recoloring `household_code` alone would leave the row's `id` unchanged, making it permanently unreachable by `syncSettings()`'s own lookup (`rows.find(r => r.id === rowId)`, always recomputed from the *current* code) — and fixing the `id` to match would collide with the canonical row's already-occupied primary key. Deletion, not update, was the only structurally valid option for this one row.

**Content comparison showed the canonical row was not a strict superset**, ruling out "just delete, it's stale" as an assumption rather than a finding: newer/richer configuration overall (named person instead of "Person 1", a payday schedule, `aiProvider: gemini` instead of unset, a larger brand list) — but a genuinely *different* `personId`, meaning that one field could represent real information loss, not just staleness. Before treating it as safe to lose, every location a `personId` can exist in the entire codebase was traced (exactly two: `MealSlotItem.individualAssignments` keys and `MacroLogEntry.personId` — confirmed via a full grep, including a check for alternate spellings) and checked: 0 references in local `mealPlanTemplates`, 0 in local `macroLogs`, 0 in local `mealPlanDays` (9 records), and — specifically, not just cloud `meal_plans` generally — a live query filtered to exactly the 3 stale `meal_plans` rows about to be recolored, since those were the rows most likely to have been written by the same device/session as the stale `sync_settings` row and could have resurrected the same dangling reference on recolor. All zero. The `personId` was confirmed dead with a complete evidence trail before deletion was treated as safe.

**Execution, staged and verified before commit.** A full 22-row snapshot was exported first, independent of the transaction. Then, inside one open transaction: `UPDATE` on `ingredients`/`meal_plans`/`grocery_lists` (`household_code <> 'Angelo-Family-2026'` → canonical), each with `returning` checked against the expected count (17/3/1) before proceeding; `DELETE` on the one stale `sync_settings` row, `returning` output visually confirmed as the stale payload, not the canonical one. A re-scan of all 4 tables inside the still-open transaction confirmed exactly one `household_code` value per table before `commit`. **Post-commit verification**: `ingredients` 6,263 rows / `meal_plans` 12 / `grocery_lists` 8 / `sync_settings` 1, every row exclusively `Angelo-Family-2026`, matching `households.code` byte-for-byte — closes the specific risk the audit above identified.

**Found during this review and deliberately deferred, not folded into this fix**: **Option B** (case-insensitive `is_member_of_code()`/`is_writable_member_of_code()`) turned out to be unsafe as a standalone 2-function change — `households.code`'s uniqueness constraint is case-*sensitive*, so nothing today stops a second, genuinely different household from being created with a code that's a case-fold of an existing one; making the comparison functions case-insensitive without also adding a case-insensitive uniqueness constraint on `households.code` would let an attacker register such a household and inherit real membership-based access to the target's exact-cased data — turning "must know the exact code" into "must know the code in roughly any casing." No current collision exists among the 7 real rows (checked live), so this isn't an active problem, and normalization above removes the current need for the fix — but if it's ever implemented, the uniqueness-constraint companion is a precondition, not an optional hardening. Separately, `fetchCloudRows()`/`upsertCloudRow()`/`deleteCloudRow()` (`db/supabase.ts:660-694`) remain independently case-sensitive regardless of any RLS-layer fix — a future re-drift through any of the three still-un-normalized entry points would silently miss data client-side even with Option B in place, since these functions would simply never request the mis-cased rows. Both logged as their own separate `OPEN_ITEMS.md` entries, explicitly not bundled here.

**What Phase 3 still needs**: this remediation closes the specific data-dependent precondition the audit found — the bridge clause is no longer covering for any casing variance, since none exists anymore. The bridge-*removal* SQL itself (drop/recreate the 4 policies per table, dropping the `household_code = 'Angelo-family-2026' or` clause) has not been written yet — that's separate, not-yet-requested work.

### Dev Tools access control (added 2026-07-23)

`/dev-tools` (nav item + route, both gated) is the app's first feature to actually *consume* the owner/contributor/readonly role system for something beyond household-member management itself. Gate logic lives in `src/hooks/useIsHouseholdOwner.ts`, consumed by both `AppLayout.tsx` (hides the nav item) and `DevToolsPage.tsx` (redirects the route itself to `/ingredients` — the nav being hidden alone is not real access control, since the URL is still typeable).

**Important distinction — there are two different "owner/contributor/readonly" concepts in this codebase, and Dev Tools deliberately uses only one of them:**
- **Real household member role** (`household_members.role` in Supabase, read via `getMyHouseholds()` in `db/auth.ts`) — DB-backed, RLS-protected, settable only by an existing owner via the "Manage members" UI. **This is what gates Dev Tools.**
- **`settings.familyShareRole`** — a plain local settings field, self-declared by whoever's using the device, used only for client-side Family Share push/pull gating (see above). Trivially editable by anyone in Settings. **Never used for Dev Tools** — using this instead would have been a real access-control hole.

**Resolution logic (revised 2026-07-24, fallback removed 2026-07-24 — see bug and risk-review below):** signed in → fetch the user's households → try to find the one whose `code` case/whitespace-insensitively matches this device's *active* `householdSyncCode` → if found, true only if that specific membership's role is `'owner'`. **If no confident match is found at all (code unset, stale, or a deeper mismatch than casing), this fails closed — `false`, full stop.** No cross-household fallback.

**🐛 Real bug, found and fixed 2026-07-24:** the app's real production household had `households.code = "Angelo-Family-2026"`, but the `household_code` actually stamped on that same household's synced data rows was `"angelo-family-2026"` / `"Angelo-family-2026"` (mixed casing across rows — confirmed directly against the live database with a service_role query). `settings.householdSyncCode` on the affected device held one of the lowercase variants, so the original exact-match check silently failed for a genuine, verified owner — no error, no indication anything was wrong, just an absent nav item. Not a caching or timing issue (the user had already hard-refreshed and fully restarted the app with the same result before this was reported) — a pure string-equality bug. **Fixed by normalizing casing/whitespace before comparing — that alone resolves this specific bug, with no need for a broader fallback.**

**🐛→⚠️ Second look, same day: the fallback that first shipped alongside the casing fix was itself a regression risk, and was removed.** The initial 2.5 fix paired the casing normalization with a second change: if no active-household match resolved at all, fall back to "owner of any household this signed-in account belongs to," reasoned as low-risk since Dev Tools has no cross-household data access. On review this didn't hold up as a durable design: it fires on *any* unresolved match, not just the casing case (unset code, stale code, a future regression in `getMyHouseholds()`), and it would silently reopen exactly the scenario the original strict design was meant to prevent — a contributor of the household actually in use, who happens to separately own some unrelated household, getting Dev Tools access to the one they don't own. It was "safe" only because today's one Dev Tools entry (the Ingredient Converter) happens to show nothing household-specific — an accidental property of current content, not an enforced constraint, and the page's own code comment explicitly commits future tools to not needing to revisit this gate. **Removed the fallback entirely; an unresolved match now fails closed (`false`).** This intentionally reopens the original narrow risk the casing fix's fallback was trying to also cover — a genuine owner whose active-household match fails to resolve for some *other*, not-yet-seen reason would now lose Dev Tools access too, surfacing as an apparent missing feature rather than an error — accepted as the right tradeoff over silently granting access to the wrong person.

**No fallback *access* path exists on purpose** — matching logic aside, there is still no local PIN, no device flag, no offline override, no path to `true` other than a confidently-resolved owner membership on the active household. A household that has never set up Account/Cloud Sync at all gets the same "absent" outcome as a signed-in contributor: hidden nav item, and typing `/dev-tools` directly redirects away with no error message or explanation (not "locked," just not there). Verified directly: fresh install with no Supabase configured, and Supabase configured but not signed in — nav item absent, direct navigation redirects, zero console errors, in both. **The positive "real owner" path (case-insensitive match) was independently live-verified on 2026-07-24**, before the fallback was removed — a disposable Supabase test user + household + owner membership were created with the same deliberately-mismatched casing as the real bug, signed in through the actual app UI via Playwright, and confirmed: Dev Tools nav item appears, `/dev-tools` loads without redirecting, page content renders, zero console errors. That case-insensitive matching code is unchanged by the fallback removal, so this verification still stands; **the fallback removal itself (fail-closed behavior for an unresolved match) was verified by code review only, not re-run live** — the live-test setup needs a Supabase service-role key and a connected browser, neither available in the session that made this change.

**What's in Dev Tools today:** two entries. The **Ingredient Converter** (`public/dev-tools/script.py`, downloadable, run locally in the household's own Python environment — the app only hosts the file, instructions, and warnings, it never executes anything) and the **Barcode Duplicate Finder** (client-side, runs in-app — see below). Built to be extensible — additional tools are meant to be added as sibling sections in the same page, not a rearchitecture.

**🐛 Real bug, found and fixed 2026-07-24: the Ingredient Converter silently stripped leading zeros off barcodes.** In `row_to_ingredient()`, `script.py` parsed the barcode ("code") column via `str(int(float(barcode_raw)))` — round-tripping an identifier through numeric conversion, which drops any leading zero (`"0079492041754"` → `"79492041754"`). Confirmed as a real, not hypothetical, production problem: the user found 8 duplicate ingredient pairs in the live household database where the same physical product had been imported twice under two different-looking barcodes purely because one import kept its leading zero and the other lost it — defeating barcode-based duplicate detection for exactly those pairs. Investigation found the bug was worse than the symptom suggested: pandas' own automatic dtype inference on an all-digit column strips the leading zero **before `row_to_ingredient()` ever runs** — confirmed live for both CSV and XLSX, including an XLSX cell where the source genuinely stored the barcode as text with the zero intact. A fix scoped only to the `row_to_ingredient()` parsing logic would not have worked; the value is already corrupted by the time that function sees it. **Fixed in script.py v5** two ways: (1) `process_file()` now forces the barcode column to string dtype at `pd.read_csv`/`pd.read_excel` read time — the only point the zero can actually be preserved; (2) `row_to_ingredient()` no longer touches `float()`/`int()` at all for the barcode field, keeping the original string exactly as given, with a defensive (not primary) fallback for the case something upstream still hands it a float. Verified directly: reproduced the pandas dtype-inference loss against a real tab-separated OFF-style export and a text-cell XLSX, confirmed the old code lost the zero in both, and confirmed the v5 fix preserves it end-to-end through `process_file()` → `row_to_ingredient()` in both formats, plus edge cases (missing barcode column, no barcode value, a defensive-path float input). **Anyone who ran an earlier version of the converter should assume their imported data may have this same duplicate pattern** — re-running the fixed script does not retroactively fix data already imported; use the Barcode Duplicate Finder below to check.

**Barcode Duplicate Finder (added 2026-07-24, Merge/Keep/Skip/Delete actions added 2026-07-24):** a one-time cleanup companion to the bug above. `src/utils/barcodeDuplicateScan.ts`'s `findLeadingZeroBarcodeDupes()` loads all (non-archived) ingredients, strips leading zeros from every variant barcode, and groups by the stripped value — surfacing any group where more than one *distinct raw string* maps to the same stripped value (a group where every entry already shares the identical raw string is a plain, ordinary duplicate, not this bug, and is deliberately not flagged). Runs entirely client-side against the local IndexedDB data, on a manual "Scan" button click — nothing runs automatically. Each result group now has real actions, not just a review link: a **Keep** radio (defaults to the entry with the longer/more-complete raw barcode), **Merge into "…"** per non-keep entry (see Section 4's "Merging duplicate ingredients" for the full mechanics — this is the same shared `mergeIngredients()` the Ingredients page's general Merge button uses), a per-entry **Delete** with a reference-check warning (via `countIngredientReferences()`), and a group-level **Skip this pair** (session-only, not persisted). Verified: the grouping/normalization logic was tested against realistic mock data (two real leading-zero pairs plus deliberate control cases) and correctly found only the real pairs; the merge repointing logic was separately verified against mock recipes/grocery-lists/macro-logs (16/16 checks); `npm run build` passes. Deployment itself was confirmed live by fetching the exact production-hashed JS bundles directly and grepping for the new UI strings. **Since confirmed working end-to-end by the user against real data**: all 8 real leading-zero duplicate pairs in the live household database were resolved through this exact UI (Keep defaults verified correct, Merge action used for all 8), a fresh scan afterward showed 0 remaining pairs, and the discarded ingredients were confirmed gone — see `TEST_FIXTURES.md` for the last 3 pairs' full data, captured before merging.

## 14. Build Notes & Decisions

### Key architectural decisions (original, still true)
- React PWA first; native APK conversion (if it ever happens) stays a later, separate step — one codebase either way.
- IndexedDB for all local storage; the app works fully offline after first load.
- AI provider is pluggable — never hard-coded to one vendor.
- The ingredient database is the single source of truth for all macros and costs app-wide.
- Nothing should block the user — warnings are subtle/non-blocking; optional features are truly optional; data is never deleted silently (archive-before-delete, confirm-before-reset).

### Newer decisions worth recording
- **Selective click-outside-to-close on modals** (2026-07-22): read-only modals close on backdrop click as before; modals with unsaved editable input now show a "Discard changes?" confirm instead of silently closing, via a shared `useConfirmClose` hook + `ConfirmDiscardDialog` component. Explicit X/Cancel buttons stay immediate/unguarded by design — only backdrop click and (where a modal already had one) Escape go through the guard. Fixed two real data-loss bugs in the process (`ReferenceEditor`, `RecipeImportModal` mid-photo-capture).
- **Settings page container width** (2026-07-22): the page is capped at 1280px and centered as one block (header + checklist + tabs/content together), and each tab's form content is centered within its content pane rather than left-aligned — see Section 3. The other five main pages (Ingredients, Cookbook, Meal Plan, Macros, Grocery) use grids/flex-rows with no artificial width cap and don't have the equivalent issue; audited and confirmed via repo-wide search, no changes needed there.
- **Documentation drift is actively tracked now**: an audit on 2026-07-22 found the in-app Help page and this reference document had both drifted significantly out of sync with the real app (most notably: neither mentioned Account sign-in at all). Both were brought current the same day. The lesson driving this document's existence going forward: update it *as part of* landing a significant change, not as a separate later cleanup pass.
- **Ingredients-table schema migration** (2026-07-22): found and fixed a real data inconsistency directly in the Supabase `ingredients` table — 744 variants (out of 6,130 rows / ~6,142 variants) stored their macro fields flat on the variant object (`variant.calories`, `variant.fat`, etc.) instead of nested inside `variant.macros.{}`, which is the only shape the app's own code ever reads (`variant.macros.calories`). Root cause not fully diagnosed (likely an older import/write path that predated the nested-macros convention), but the fix was purely structural — move the 9 known macro fields (`calories`, `protein`, `carbs`, `fiber`, `sugar`, `fat`, `sodium`, `saturatedFat`, `transFat`, plus `alcohol` where present) into `macros: {}` and delete them from the top level, no value changes. Full table backed up to a local JSON file before any writes; dry-run reviewed before applying. Ran via a one-off Node script using the Supabase **service_role** key (required a one-time `grant select, insert, update, delete on public.ingredients to service_role;` — this project's table grants had only ever covered `anon`/`authenticated`, a gap from the same migration work described in Section 11). 741 of 744 were unambiguous; 2 more (Mustard, Lemonade) had a stray *partial* nested `macros` object whose one populated field agreed with the flat data, so those were merged in as the complete set too. One (Dill Pickle) had a real value conflict and was deliberately left untouched — see the flag in Section 4.
