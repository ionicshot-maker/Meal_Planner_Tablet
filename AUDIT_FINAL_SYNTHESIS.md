## 2. Systemic Patterns

Revisiting the cross-phase themes named during the audit, now that all phases are complete:

### "Trusted, not verified" — **confirmed as the audit's strongest systemic pattern**

This pattern was independently rediscovered in **four separate phases**, on unrelated data: Phase 1 (the sodium-unit-bug heuristic, the fuzzy-match default), Phase 3 (Gemini nutrition-lookup macro fields, the oz→g heuristic — structurally identical to Phase 1's sodium finding, in a completely different subsystem), and Phase 4 (person-profile numeric fields, the `householdSize` stepper). Each instance is narrow and individually low-severity, but the *recurrence* across data-integrity, AI-integration, and configuration layers — three phases that shared no methodology and weren't looking for each other's findings — is what elevates this from "a few similar bugs" to a genuine architectural habit: **this codebase generally trusts that a value entering the system (from an AI response, a heuristic correction, or a form field) is well-shaped, and validates presence/existence far more often than it validates type or range.** This is consistent with a project that has, by its own extensive documented history, repeatedly found and fixed *specific* instances of bad data (the scale-inflation bug, the sodium bug, the barcode write-path bug) reactively, one at a time, rather than having a general boundary-validation layer. The pattern is real, consistent, and — importantly — every confirmed instance found this audit is a **plausible concern**, not a **confirmed active defect**: nothing was caught actually misbehaving in production from this pattern during the audit itself, which matters for calibrating how urgently to treat it.

### Silent divergence between related values — **valid, narrower than originally framed**

The clearest instance is `householdSize` vs. `people.length` (Phase 4) — two values that should track each other, don't always, and nothing reconciles or warns when they disagree. The nested-settings shallow-merge gap (`nutrientToggles`/`ingredientDisplay`, Phase 4) is related in spirit (two representations of "what a household's settings should look like" — stored vs. default — that could silently diverge for a future field) but is a **latent** risk, not an active one; it has never actually been triggered. This pattern is real but is best described as an isolated defect (`householdSize`) plus one latent structural risk, not evidence of a wider "values silently drift apart" problem across the codebase — the extensive historical ingredient/recipe count reconciliation work (documented in `OPEN_ITEMS.md`, referenced throughout this audit but not re-litigated) is the same *shape* of concern and was already handled with real rigor when it mattered.

### Documented behavior vs. actual behavior — **confirmed, and the audit's second-strongest pattern**

At least **five independent instances** were found across four phases: `archiveAndPrune()` vs. "Shopping History" (plural) (Phase 1); the stale PLU/barcode-length prompt wording in `gemini-receipt-scan` (Phase 3); `macroHistoryDays`'s "retention window" framing vs. the dead `pruneOldEntries()` (Phase 1); the stale pre-Phase-3 setup-SQL shown to new households (Phase 5); and — by far the most consequential — **Family Share described as fully working in three separate Help/FAQ locations while completely non-functional** (Phase 5/6). This project has a real, recurring tendency for prose (comments, prompts, reference docs, in-app help) to stop matching code the moment the code changes, without a corresponding process to catch it. The Family Share instance is qualitatively different from the other four, which are all narrow, low-consequence wording staleness — it is the one case where the *documentation actively tells a user to do something that cannot work*, discovered specifically because Phase 6 thought to cross-check Help content against Phase 5's live-tested finding rather than treating the two phases' scopes as fully separate.

### Promised functionality without an effective execution path — **confirmed, three real instances**

Family Share (the major instance); `macroHistoryDays`'s implied age-based pruning (no execution path — `pruneOldEntries()` is never called); and `archiveAndPrune()`'s implied multi-list history (capped at 1, contradicting its own documentation). All three are now folded into the finding inventory above; grouping them here confirms this is a genuine, if modest, recurring shape — a setting or feature description that implies more retained capability than the code actually delivers.

### Dead/unreachable paths — **real, but isolated implementation debt, not systemic**

`pruneOldEntries()` and `deleteMealPlanDay()` (both Phase 1) are the only two clear instances found across all seven phases. Two isolated instances in an application of this size and history do not constitute a systemic pattern — this is ordinary, expected implementation debt (a function written for a feature that was later simplified or never fully wired up), not evidence of a broader "code rots and nobody notices" problem. Notably, Phase 7's search for *new* dead/unused resilience-recovery code found none — the gap there was the *opposite* shape (a mechanism that exists in one place but was never *extended* to others), not dead code.

## 3. Elevated Findings Review

The three findings elevated during the audit were: Family Share's outage, the backup-restore settings loss, and the `householdSize`/`people.length` divergence. Reassessed now with the complete record:

**Family Share remains the single highest-priority finding of the entire audit, and its priority has only strengthened.** It is now the only finding in the entire audit corroborated by **four independent phases** using four different methodologies (data-movement code review, security/RLS reasoning followed by a real live test, user-facing documentation cross-check, and resilience/failure-mode characterization) — and it is the only finding with an actual, captured, verbatim production error as direct evidence, not just code-level reasoning. Nothing in Phases 6 or 7 displaces it; if anything, they deepened it by showing the *consequences* (users are told it works, and get an unhelpful raw error if they try) rather than just the *mechanism*.

**A fifth item was briefly considered for this ranking and has been withdrawn.** Phase 5's credential-exposure finding was initially elevated to rank #2 on urgency grounds. On review, this classification did not incorporate a clarification given directly by the user: the finding describes an intentional, local-only audit-access mechanism, not an accidental exposure. It has been reclassified as Explained/non-issue and removed from this ranking.

**Backup-restore settings loss and `householdSize`/`people.length` divergence remain valid, real, and worth tracking** — the audit's later phases didn't add dramatic new weight to either (Phase 6 added a user-facing framing to the former; neither was touched by Phase 7) — but they are now more accurately understood as **the second and third most important findings**, given the sharper evidence base built up around Family Share (see the reclassification note above regarding the credential item originally ranked here).

**Revised priority ordering, evidence-based**: (1) Family Share outage, (2) backup-restore settings loss, (3) `householdSize`/`people.length` divergence, (4) owner-self-removal (newly confirmed, included in this tier given it's a clean, direct, confirmed gap rather than a "plausible concern"). This is a factual re-ranking based on evidentiary weight and urgency, not a remediation recommendation.

## 4. Audit Balance Review

This audit surfaced **mostly isolated, individually-modest defects and documentation/behavior drift, plus one confirmed broken secondary feature — not evidence of deep architectural rot** (see §3's reclassification note for a credential-scan item originally counted in this characterization and since withdrawn). Weighing the categories:

- **Isolated bugs**: the majority of confirmed issues (dead functions, the setup-SQL staleness, the `SetupChecklist` persistence gap, the `openDB()` handler gap) are narrow, one-off, and independently fixable without touching anything else.
- **Documentation/UX drift**: a real, recurring category (§2), but every instance except Family Share is low-consequence wording staleness rather than active harm.
- **Design weaknesses**: `householdSize`/`people.length`, the Family Share vs. Household Sync feedback-quality gap, and the draft-recovery asymmetry are genuine design gaps — places where a considered decision was either never made or was made for one sibling feature and never extended to another.
- **Systemic architectural patterns**: exactly one candidate rises to this level — "trusted, not verified" — and even that is better described as a *consistent habit* (validate presence, not shape) than a *flaw in the architecture itself*; the atomicity/transaction architecture, by contrast, is genuinely systemic *and* was found sound everywhere it was tested.

**Overall characterization**: this is a well-built, actively-and-honestly-maintained application whose core data-integrity and security architecture held up under sustained, adversarial-minded scrutiny across seven independent phases, with a small number of real defects (most prominently one broken secondary feature) and a consistent, correctable pattern of trusting values at system boundaries rather than validating them. It is not a codebase in crisis; it is a mature codebase with a normal, bounded amount of accumulated debt and one feature (Family Share) confirmed nonfunctional in production — not, as this document originally characterized it here, a side effect of the Phase 3 security fix; see the correction note immediately below. (A credential-scan item originally counted alongside this characterization was separately reclassified as explained, not a hygiene lapse — see §3.)

**Correction (post-synthesis root-cause investigation): the causal claim above has been revised.** This document originally stated Family Share "quietly broke as a side effect of an otherwise-correct security fix," attributing the outage to the Phase 3 RLS bridge-removal work. A subsequent root-cause investigation found this attribution inaccurate: the bridge clause was a literal string comparison against the primary household's own canonical code and could never have matched a `:family`-suffixed Family Share code, whether the bridge was present or removed. Family Share's access was therefore never protected by the bridge in the first place — it has depended on `is_member_of_code()`'s real-membership check (which requires a `households` row no `:family`-suffixed code has ever had) since whenever that membership-based RLS model was first introduced, well before Phase 3 existed. There is no evidence this household ever used Family Share successfully at any point — this session's own live test found its Family Share Code field empty and "Last synced on this device: never" immediately before a code was generated for testing. The finding that Family Share is broken is unchanged and remains fully valid; only its attributed cause has been corrected.

## 5. What Was Confirmed Good

Treated here as first-class results, not footnotes:

- **The core household-isolation security model held up.** `is_member_of_code()`/`is_writable_member_of_code()` were re-read structurally in Phase 5 and found consistent with the documented, already-adversarially-tested Phase 3 RLS fix; nothing found anywhere in the audit constitutes a cross-household data leak. The one real gap found (Family Share) is a case of **too little access** for legitimate users, not unauthorized access for illegitimate ones — the opposite failure direction from a security breach.
- **Atomicity discipline is genuinely systemic and genuinely solid.** Every multi-step local mutation that should be atomic — `mergeIngredients()`, `applyReceiptSaveBatch()`, `executeImport()`, `performReset()`, both duplicate-resolution functions' local halves — was independently re-confirmed atomic in three different phases (1, 2, 7), the last of which specifically checked this against a hard browser crash rather than just a thrown error, using the platform's own IndexedDB transaction guarantee rather than assuming the application code alone was responsible.
- **The Gemini fallback and model-discovery infrastructure is sound and unregressed.** A substantial, multi-phase engineering effort (21+7 hardcoded literals consolidated, 7 of 8 functions wired for fallback reporting, three phases of dynamic model discovery) was re-verified this session with a fresh repo-wide grep and found to have zero new hardcoded call sites and zero regressions — a genuinely clean re-audit result, not a soft one.
- **The scale-inflation bug fix is not just intact — it's structurally confirmed unable to recur elsewhere**, because no other AI integration point in the app returns the kind of spatially-scaled coordinate data that made the original bug possible.
- **Cloud Sync's retry/resume model is well-matched to its actual failure mode.** Its per-record, non-transactional write shape looked, on first inspection, like it might violate the project's own atomicity standards — but tracing it through showed this is a deliberate, correct design choice for an idempotent, resumable operation, re-confirmed resilient against a real interruption scenario, not just a theoretical one.
- **The four startup repair/migration functions are self-healing by construction** — none of them need an explicit resume mechanism, because each one's own idempotent per-item check makes a mid-pass interruption naturally and correctly recoverable on the next load.
- **The credential architecture is sound, including the one item that initially looked like a possible lapse.** Zero `service_role` dependency exists anywhere in deployed code; the real anon key has already been migrated to the new `sb_publishable_` format; and a credential-scan hit in a local, git-ignored, untracked tool-permission cache — initially flagged with urgency — was confirmed directly with the user afterward to be an intentional, local-only mechanism supporting audit/database-access work, not an exposure (see §3).
- **Household create/join is resilient to interruption at every point checked**, including a scenario (browser closing between a successful create/join RPC and the local settings save) that could plausibly have left a device unable to find its own household — it doesn't, because membership lookup is server-side and independent of local state.
- **Offline behavior matches what the app tells users to expect.** The Help page's claim that everything except barcode/USDA/Gemini lookups and cloud sync works offline was checked structurally and holds.
- **Malformed-input handling across every import pipeline reviewed (JSON Import, Receipt Scanner, Bulk Entry) rejects bad shape cleanly rather than silently corrupting data** — a consistent, positive pattern across multiple independently-built features.

## 7. Pre-Supabase Assessment

Two narrow questions, answered retrospectively:

**Was performing a full audit before the final Supabase legacy-key deactivation justified?** Yes, clearly, though not for the reason the deactivation task itself would have predicted. The audit did not change the risk calculus of the deactivation question specifically — Phase 5 re-confirmed exactly what the original 2026-07-28 investigation already found: zero deployed dependency on `service_role`, and the real anon key already migrated to the new format. If the only goal had been "is it safe to deactivate the legacy key," the audit's answer is the same as it was before Phase 0 began. The justification for the broader audit comes from everything else it found *along the way*: a fresh credential-scan hit that a narrowly-scoped "just deactivate the key" task would never have surfaced for clarification (though, per §3, it turned out to be an intentional, local-only mechanism rather than a real exposure); a completely broken secondary feature (Family Share) with real user-facing consequences; a confirmed account-management gap (owner self-removal); and a recurring, now well-evidenced architectural pattern (trusted-not-verified) worth being aware of going forward. None of these would exist in the project's known-issues record without this audit.

**Did the audit discover anything that would have made performing the Supabase step first a mistake?** No. Nothing found in any phase suggests the legacy-key deactivation itself is riskier than previously understood, and nothing found depends on the legacy key remaining active — the RLS security model, the household-isolation guarantees, and the credential architecture were all re-confirmed sound independent of that specific pending action. The decision to audit broadly first was not a response to a discovered risk in the deactivation step itself; it was, in retrospect, simply the more thorough choice, and it paid for itself by surfacing several unrelated items (most notably the Family Share outage, plus a credential-scan question that was surfaced and directly clarified with the user — see §3) that are now known and documented rather than latent.
